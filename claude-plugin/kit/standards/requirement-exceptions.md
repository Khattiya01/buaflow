# Requirement coverage และ approved exception (EP-002)

`standards/readiness-levels.md` ข้อ 4 เขียนไว้ตั้งแต่วันที่นิยาม R0–R4 ว่า
**"exception/waiver เป็นการยอมรับความเสี่ยง ไม่ทำให้ control กลายเป็น `pass`"**
แต่ไม่เคยมีที่ให้เขียน exception ลงไปเลย เอกสารนี้คือที่นั้น

## ปัญหาที่มันแก้ — และมันเกิดขึ้นในเรพนี้แล้ว

reference app ทั้งสามตัวมีหัวข้อ **"Known limitations (not fixed — documented instead of hidden)"**
อยู่ใน `docs/security-notes.md` มีของจริงอยู่ในนั้นสี่ถึงห้ารายการต่อแอป ทั้งหมดซื่อสัตย์
และทั้งหมด**มองไม่เห็นด้วยเครื่อง**: ไม่มีเจ้าของ ไม่มีระดับความเสี่ยง ไม่มีวันที่จะกลับมาดู
และไม่มี gate ไหนอ่านมัน

ก่อนมี artifact นี้ การ ship ช่องโหว่ที่รู้อยู่แล้วและยอมรับแล้ว มีสามทางและแย่ทั้งสามทาง:

| ทาง | เกิดอะไรขึ้น |
|---|---|
| ประกาศ `pass` ใน readiness manifest | โกหก และ manifest ทั้งใบเชื่อไม่ได้ต่อจากนั้น |
| ใช้ `not-applicable` | ผิดความหมาย — มันแปลว่า "ไม่มีความสามารถนั้นอยู่" ไม่ใช่ "รับความเสี่ยงไว้แล้ว" และใช้ได้แค่ 4 conditional control |
| เขียนไว้ใน prose | ซื่อสัตย์ แต่ไม่หมดอายุ ไม่มีเจ้าของ และไม่มีใครถูกเตือนอีกเลย |

## สัญญา

ไฟล์ `docs/evidence/requirement-coverage.json` (`schemas/requirement-coverage.schema.json`)
ตรวจด้วย `node .claude/requirement-coverage.js`

**requirement หนึ่งข้อตอบได้ด้วยของอย่างใดอย่างหนึ่งเท่านั้น:**

| | แปลว่า |
|---|---|
| `proof[]` | มีหลักฐานที่ทำซ้ำได้ — command, ไฟล์ในโปรเจกต์ หรือ URL ของ run จริง |
| `exception{}` | ยังพิสูจน์ไม่ได้ และมีคนชื่อหนึ่งรับความเสี่ยงไว้จนถึงวันหนึ่ง |

มีทั้งคู่ = อย่างใดอย่างหนึ่งโกหก · ไม่มีเลย = requirement ที่รับปากไว้แล้วไม่มีใครตอบ
ทั้งสองกรณีทำให้ตก

### exception ต้องมีอะไรบ้าง

| ฟิลด์ | ทำไมถึงบังคับ |
|---|---|
| `owner` | ชื่อคนที่ถามต่อได้ ไม่ใช่ชื่อทีม — ความเสี่ยงที่ทุกคนเป็นเจ้าของคือความเสี่ยงที่ไม่มีใครเป็นเจ้าของ |
| `reason` | อย่างน้อย 20 ตัวอักษร บอกว่า**ทำไมถึงยอมรับ** ไม่ใช่บอกว่าขาดอะไร |
| `risk` | `low` / `medium` / `high` — รายงานรวมยอดตามระดับ ให้เห็นว่ากองความเสี่ยงที่รับไว้ใหญ่แค่ไหน |
| `acceptedOn` | วันที่ตัดสินใจ ใช้คำนวณว่ารับไว้ยาวแค่ไหน |
| `expiresOn` | **หัวใจของทั้งหมด** — exception ที่ไม่มีวันหมดอายุแยกไม่ออกจาก requirement ที่ไม่มีใครตั้งใจจะทำ |
| `compensatingControl` | ไม่บังคับ แต่ถ้ามีอะไรยืนแทนหลักฐานที่ขาด ให้เขียนไว้ |

`expiresOn` ที่เลยมาแล้ว = **FAIL ไม่ใช่ warning**

### proof ที่เป็น manual ล้วนไม่นับเป็น proof

ถ้านับ กลไกทั้งหมดนี้เลี่ยงได้ด้วยประโยคเดียว (`"ตรวจด้วยมือแล้ว"`) — ซึ่งเป็นสิ่งที่
`readiness.js` พูดไว้อยู่แล้วว่า manual evidence ทำซ้ำไม่ได้ ของที่ตรวจด้วยตาในเซสชันที่ไม่มีอยู่แล้ว
ไม่ใช่หลักฐาน มันคือ **exception ที่ยังไม่ได้เขียน** และวิธีที่ถูกคือเขียนมันออกมา
(`nextjs-postgres-crud` REQ-004 คือตัวอย่างจริงของเคสนี้)

## หน้าต่างเวลาเป็นนโยบายของผู้ตรวจ

`--max-window-days N` จำกัดว่า "รับความเสี่ยงไว้ล่วงหน้าได้นานที่สุดกี่วัน" ไม่ใส่ = รายงานอย่างเดียว ไม่ตัดสิน
เพราะถ้าไม่มีเพดาน `expiresOn: "2099-01-01"` ก็ผ่าน ซึ่งคือช่องโหว่เดียวกับที่ EP-010 ปิดด้วย `--max-age-days`

`npm run check` ของ kit ใช้ **90 วัน** กับ reference app ทั้งสามตัว — เลขเดียวกับที่
`evidence-freshness.yml` ใช้ · `gate.js` **ไม่** ใส่ค่านี้ให้โปรเจกต์ผู้ใช้โดยตั้งใจ:
ความเสี่ยงที่ internal tool รับได้กับที่ธนาคารรับได้ไม่เท่ากัน ใส่เองใน CI ของโปรเจกต์

## ต่างจาก evidence-freshness (EP-010) ตรงไหน

ทั้งคู่มีวันหมดอายุ แต่คนละชนิด และผลลัพธ์จึงต่างกันโดยตั้งใจ:

| | evidence-freshness | approved exception |
|---|---|---|
| วันหมดอายุเป็นของใคร | ผู้ตรวจกำหนด (`--max-age-days`) | **คนที่เซ็นรับความเสี่ยง** กำหนดเอง |
| ทำไมถึงต่าง | หลักฐานที่ประกาศอายุตัวเองได้ ก็ประกาศว่าสดตลอดกาลได้ | มันคือสัญญาที่มีชื่อกำกับ ไม่ใช่คุณสมบัติของหลักฐาน |
| เลยกำหนดแล้วได้อะไร | `EXPIRED` (exit 4) — ไม่ใช่ความผิดของใคร มันแค่เก่า | `FAIL` (exit 1) — สัญญาที่ไม่ถูกรักษา |

## additive

โปรเจกต์ที่ไม่มี `docs/evidence/requirement-coverage.json` ไม่ถูกตรวจข้อนี้เลย และ `gate.js`
ไม่เปลี่ยนพฤติกรรมใด ๆ ตามนโยบายของ `standards/artifact-versioning.md` — นี่คือเหตุผลที่
3.1.0 เป็น MINOR ไม่ใช่ MAJOR ตาม `standards/release-policy.md`

|---|---|---|

| `reference-apps/react-fastapi-postgres-crud` | 13 | 4 (rate limit, CSRF, key rotation, client-side route guard) |
| `reference-apps/expo-fastapi-postgres-sync` | 17 | 4 (rate limit, CSRF, key rotation, last-write-wins ที่ทิ้งเนื้อหาของ edit ที่แพ้) |

ไม่มีข้อไหนในตารางนี้ถูกประดิษฐ์ขึ้นใหม่: ทุกข้อมาจาก "Known limitations" ใน `docs/security-notes.md`
หรือจากแถวที่มีอยู่แล้วใน `docs/requirements-traceability.md` (REQ-004 ของ `nextjs-postgres-crud`
คือแถว audit trail ที่หลักฐานเดียวของมันคือการดูด้วยตาใน session ที่ไม่มีอยู่แล้ว) งานของ EP-002
คือทำให้ของที่ซื่อสัตย์อยู่แล้วมีเจ้าของ มีวันหมดอายุ และเครื่องมองเห็น

มีรายการเดียวใน "Known limitations" ที่**ไม่**ถูกแปลงเป็น exception โดยตั้งใจ: local task id ของ
`expo-fastapi-postgres-sync` ที่มาจาก `Math.random` — prose ของมันอธิบายเองว่า id ไม่ได้ถูกใช้เป็น
capability token หรือความลับที่ไหนเลย จึงไม่มี requirement ข้อไหนที่ไม่ถูกทำตาม มันเป็นบันทึกการออกแบบ
ไม่ใช่ความเสี่ยงที่รับไว้ และ exception ที่ไม่มี requirement รองรับก็คือการทำให้กองความเสี่ยงดูใหญ่เกินจริง
