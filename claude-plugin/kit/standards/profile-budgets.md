# Budget ที่มาจาก application profile (EP-007)

การ **วัด** เสร็จไปนานแล้วและถูกบังคับที่ R3 — ทุก reference app รัน axe และ performance budget
แล้วส่ง JSON เป็นหลักฐาน สิ่งที่ไม่เคยมีคือคำว่า **profile-specific** ที่ทั้ง roadmap และ
`standards/deployment-ready-contract.md` ใช้: `application-profile.schema.json` ไม่มี threshold
สักตัว

## ปัญหาที่มันแก้

ก่อนหน้านี้หลักฐานของแอปหน้าตาแบบนี้:

```json
{ "budgetMs": 3000, "login": { "loadEvent": 47.4 } }
```

`3000` มาจากไหน? มาจากแอปนั้นเอง แปลว่า **แอปเป็นคนตั้งข้อสอบให้ตัวเองแล้วให้คะแนนตัวเอง**
content site กับ internal tool ถูกวัดด้วยไม้บรรทัดคนละอันที่ไม่มีใครเลือกอย่างตั้งใจ — ซึ่งเป็นสิ่งที่
profile contract มีไว้เพื่อป้องกันพอดี

## สัญญา

| อยู่ที่ไหน | เก็บอะไร |
|---|---|
| `application-profile` **1.1** `budgets` | **เพดาน** — แอปชนิดนี้ยอมรับได้แค่ไหน และทำไม |
| `docs/evidence/budgets.json` (`budget-evidence` 1.0) | **ตัวเลขที่วัดได้** คำสั่งที่รันซ้ำได้ และไฟล์หลักฐานที่ตัวเลขนั้นออกมา |

`budget-evidence` **ไม่มีช่องให้ใส่เพดานเลยโดยตั้งใจ** ถ้ามันมี เราก็กลับไปที่เดิม

### metric ที่รองรับ

| metric | อ่านมาจาก |
|---|---|
| `loadEventMs`, `domContentLoadedMs` | ตัวเลขในไฟล์ performance ตาม `path` ที่ระบุ |
| `axeViolations` | `violations.length` ของผล axe |
| `axeSeriousOrCritical` | จำนวน violation ที่ `impact` เป็น serious หรือ critical |

รายการนี้ปิด — profile จะกำหนดเพดานให้ metric ที่ไม่มีใครวัดไม่ได้

### กติกาที่บังคับ

1. **ตัวเลขถูก derive ใหม่จากไฟล์หลักฐานจริงทุกครั้ง** แล้วเทียบกับที่ประกาศ (ยอมให้ปัดเศษ
   ไม่ยอมให้เป็นคนละเลข) — หลักการเดียวกับสรุป licence ของ EP-004
2. **metric ที่ profile กำหนดเพดานไว้แต่ไม่มีใครวัด = ตก** ไม่วัดไม่ใช่ผ่าน
3. ทุกการวัดต้องมี **คำสั่งที่รันซ้ำได้** และไฟล์ที่มีอยู่จริง
4. วัด metric ที่ profile ไม่ได้กำหนดเพดาน = ตก เพราะมันไม่ได้ตัดสินอะไร
5. **profile ที่ไม่มี `budgets` เลย = ตก** — record ที่อ้าง profile ที่ไม่มีเพดาน คือเอกสารที่ดู
   เหมือนมีการควบคุม ทั้งที่ไม่มีอะไรควบคุม

## ผลที่ตั้งใจให้เกิด

**เปลี่ยนคำว่าแอปนี้คืออะไร แล้วเส้นผ่านเปลี่ยนตาม โดยไม่ต้องแตะตัวแอปเลย**

แอปที่โหลด 2200ms และมี axe finding ระดับ minor สองข้อ:

| profile | ผล |
|---|---|
| `internal-crud` | ผ่าน — พนักงานเปิดเครื่องมือนี้ตั้งใจและเปิดค้างไว้ |
| `content` | **ตก** — `loadEventMs 2200 > 1500` และ `axeViolations 2 > 0` |

ตัวเลขไม่ได้เปลี่ยน **มาตรฐานเปลี่ยน** และนั่นคือสิ่งที่คำว่า profile-specific ควรแปลมาตลอด
(ข้อนี้พิสูจน์ด้วยเทส ไม่ใช่ด้วยการทำให้ reference app ช้าลง — ของจริงทั้งสามตัวโหลดใต้ 50ms
และไม่มี violation เลย)

## เพดานที่ profile ที่ ship มาด้วยกำหนดไว้

| metric | `content` | `saas` | `internal-crud` |
|---|---|---|---|
| `loadEventMs` | 1500 | 2000 | 3000 |
| `domContentLoadedMs` | 1000 | 1200 | 2000 |
| `axeViolations` | 0 | 0 | 5 |
| `axeSeriousOrCritical` | 0 | 0 | 0 |

`axeSeriousOrCritical` เป็น 0 ทุก profile โดยตั้งใจ: กลุ่มผู้ใช้ที่รู้จักกันดีไม่ใช่เหตุผลที่จะ ship
หน้าที่มีคนในทีมใช้ไม่ได้เลย · ส่วน `internal-crud` ยอม minor/moderate ได้ถึง 5 ซึ่งคือความต่าง
ที่ profile นี้มีไว้แสดง และเพดานคือสิ่งที่กันไม่ให้ความยืดหยุ่นนั้นกลายเป็นไม่มีขีดจำกัด

> `internal-crud` ตั้ง accessibility budget ไว้ทั้งที่ profile เดียวกันประกาศ control
> `accessibility` เป็น `not-applicable` — ตั้งใจ: ถ้าแอปเลือกที่จะเปิดใช้ (ซึ่ง reference app
> ทั้งสามตัวทำ) นี่คือเส้นที่ต้องข้ามให้ได้

## additive

profile ที่ยังเป็น 1.0 อ่านได้เหมือนเดิม มันแค่ไม่มี budget · migrator เลื่อนเป็น 1.1 ให้โดย
**ไม่เติม budget ให้เอง** เพราะการเติมคือการตัดสินใจแทนเจ้าของ profile ว่ามาตรฐานของเขาคืออะไร ·
โปรเจกต์ที่ไม่มี `docs/evidence/budgets.json` ไม่ถูกตรวจข้อนี้เลย — 3.5.0 จึงเป็น MINOR
