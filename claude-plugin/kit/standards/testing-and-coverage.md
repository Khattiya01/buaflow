# การทดสอบและ Code Coverage

## 1. หลักการของโปรเจกต์นี้

| ชั้น | เขียนเมื่อไหร่ | ใครรับผิดชอบ |
|---|---|---|
| **Backend unit test** | **พร้อมกับ module เสมอ** อยู่ใน DoD ของ task นั้น | AI ตอนทำ task |
| **Frontend unit test** | **หลัง UI นิ่ง** (ผ่าน review เป็น done แล้ว) ผ่าน task `T-xxx-test` | AI ตอนทำ task test |
| **Integration (API)** | เมื่อ endpoint เสร็จ — Postman collection | AI ตอนทำ task |
| **E2E** | ตอนปิด feature ใหญ่ เฉพาะ critical path | AI |
| **Manual / UAT** | ก่อนขึ้น prd | คน |

> เหตุผลที่ frontend test ทำทีหลัง: ระหว่าง UI ยังปรับ การเขียนเทสไปด้วยจะทำให้ต้องรื้อเทสซ้ำๆ
> แต่ **ต้องเขียนจริง** ไม่ใช่ข้าม — จึงบังคับให้สร้าง task `-test` ตั้งแต่ตอนทำ UI

## 2. พีระมิดเทส (สัดส่วนที่ควรเป็น)

```
        E2E (Playwright)        ~5%   critical path เท่านั้น
    Integration (API/DB)       ~25%   endpoint + database จริง
  Unit (service/util/component) ~70%   เร็ว แยกอิสระ
```

อย่าทำกลับด้าน — E2E เยอะเกินไปจะช้า เปราะ และไล่หาสาเหตุยาก

---

## 3. เป้า Coverage

| ส่วน | Line | Branch | หมายเหตุ |
|---|---|---|---|
| Backend service / business logic | **≥ 85%** | ≥ 75% | นี่คือส่วนที่พังแล้วเจ็บ |
| Backend controller / route | ≥ 70% | ≥ 60% | เน้น validation + error path |
| Frontend component (หลัง UI นิ่ง) | ≥ 70% | ≥ 60% | |
| **โค้ดใหม่ในรอบนี้ (new code)** | **≥ 80%** | ≥ 70% | ← ตัวที่ Sonar quality gate ใช้จริง |

**ไม่นับ coverage ของ:** `components/ui/**` (shadcn generated), ไฟล์ config,
`*.spec.ts`, migration, ไฟล์ที่ generate อัตโนมัติ

> อย่าไล่ตาม % จนเขียนเทสขยะ เทสที่ไม่ assert อะไรเลยแต่ทำให้เลขสวยคือหนี้ ไม่ใช่ทรัพย์สิน
> เกณฑ์ที่ดีกว่าคือ **"ถ้าลบ logic บรรทัดนี้ทิ้ง มีเทสตัวไหน fail ไหม"**

## 4. เขียนเทสยังไงให้มีประโยชน์

### ต้องเทส
- business logic ทุกกิ่ง (เงื่อนไข, การคำนวณ, กติกาอนุมัติ)
- edge case: ค่าว่าง, null, 0, ค่าติดลบ, string ยาวเกิน, วันที่ข้ามเดือน/ปี, timezone
- error path และข้อความ error ที่ถูกต้อง
- สิทธิ์: role ที่ไม่มีสิทธิ์ต้องถูกปฏิเสธจริง
- บั๊กทุกตัวที่เคยเจอ (regression test)

### ไม่ต้องเทส
- library ของคนอื่น
- getter/setter ที่ไม่มี logic
- โค้ดที่ generate มา

### รูปแบบ
- ตั้งชื่อเทสเป็นประโยคที่อ่านแล้วรู้ว่าพังอะไร
  `it('ปฏิเสธการสมัครเมื่ออีเมลซ้ำ และตอบ code EMAIL_TAKEN')`
- โครง **Arrange → Act → Assert**
- 1 เทส 1 เรื่อง
- ห้ามเทสพึ่งลำดับการรัน หรือพึ่ง state จากเทสก่อนหน้า
- ใช้ factory/builder สร้างข้อมูลทดสอบ แทน fixture ยักษ์

## 5. ออกแบบ test case — เทคนิคคือพื้น ไม่ใช่เพดาน

เทคนิคข้างล่างดึง case ที่ **ต้องมี** ออกมาจาก spec หรือโค้ดด้วยวิธีที่คนตรวจทวนได้
ไม่ต้องรอว่า model วันนั้นจะนึกออกหรือเปล่า แต่มัน **ไม่ใช่รายการปิด**
ใช้เทคนิคครบแล้วต้องคิดต่อเสมอ (5.5) เพราะ case ที่พังจริงใน production มักอยู่นอกสิ่งที่ spec เขียนไว้

**ใครออกแบบ:** session หลักเป็นคนออกแบบ เพราะใช้ model ที่ทีมเลือก
- มี spec → `/spec` ออกแบบไว้ใน design.md
- ไม่มี spec → `/plan` ออกแบบไว้ใน plan.md
- ไม่มี plan → `/task` ออกแบบในขั้นยืนยันความเข้าใจ

subagent `test-writer` แค่แปลงรายการ case เป็นโค้ดเทส ถ้าเจอ case ที่ตกหล่นก็เพิ่มได้ แต่ต้องรายงานกลับ

### 5.1 ใช้เทคนิคไหนเมื่อไหร่

| เทคนิค | ใช้เมื่อเจอ | ดึง input จาก | ได้ case อะไร |
|---|---|---|---|
| **Boundary value** | ค่าที่มีขอบ: ตัวเลข, ความยาว, จำนวนรายการ, วันที่/เวลา, ขนาดไฟล์, หน้า pagination | กติกาธุรกิจ, validation (zod/DTO), NFR ปริมาณ | ทุกขอบ: ต่ำกว่าขอบ 1 · ตรงขอบ · เกินขอบ 1 (บวกค่าว่าง/0 ถ้าเกี่ยว) |
| **Decision table** | ผลลัพธ์ขึ้นกับ ≥ 2 เงื่อนไขร่วมกัน (role × สถานะ × เป็นเจ้าของ record) | ตารางสิทธิ์, กติกาธุรกิจ, AC แบบ IF…THEN | ทุก combination ที่ให้ผลต่างกัน — ยุบแถวที่ผลเหมือนกันได้ แต่เขียนว่ายุบเพราะอะไร |
| **State transition** | entity ที่มีสถานะ (draft → pending → approved, คอลัมน์ของการ์ด) | AC แบบ WHILE, Flow ใน design.md | ทุกทางเปลี่ยนที่อนุญาต + **ทางที่ห้าม** อย่างน้อยหนึ่งทางจากทุกสถานะ (ข้ามขั้น, ย้อนกลับ, ทำซ้ำ) |
| **Equivalence partition** | input ที่มีกลุ่มค่าที่ระบบปฏิบัติต่างกัน (ประเภทลูกค้า, ภาษา th/en, ชนิดไฟล์) | กติกาธุรกิจ, enum | ค่าตัวแทนหนึ่งค่าต่อกลุ่ม รวมกลุ่มที่ไม่ถูกต้อง |

เทคนิคไหนไม่เข้าเงื่อนไข → เขียนบรรทัดเดียวว่าไม่เข้าเพราะอะไร **ห้ามสร้างแถวหลอกให้ตารางดูครบ**

### 5.2 ช่องที่ spec ไม่ได้ตอบ = คำถาม ไม่ใช่การเดา

ข้อดีที่ได้ก่อนเขียนเทสสักบรรทัด: ตารางจะเผยว่า requirements ยังขาดอะไร เช่น ชื่อยาวได้สูงสุดเท่าไร
หรือ Operator ลบ record ที่ตัวเองไม่ได้สร้างได้ไหม
ช่องที่ผลที่คาดหวังไม่มีใครบอก → `[NEEDS CLARIFICATION]` ใน spec หรือรายงานเป็นคำถาม (ตอนเขียนเทสโดยไม่มี spec)
**ห้ามเดาค่าที่คาดหวังแล้วเขียนเทสล็อกมันไว้** เพราะเทสจะกลายเป็นตัวยืนยันการเดา

### 5.3 ทุกแถวต้องกลายเป็นเทส

- ตั้ง id ให้แต่ละ case: `BV-x` boundary · `DT-x` decision table · `ST-x` state transition · `EQ-x` partition · `RK-x` ความเสี่ยงนอกตาราง (5.5)
- ทุก id ต้องมีแถวใน "แผนการทดสอบ" ของ design.md และชื่อเทสควรมี id นั้นให้ grep เจอ เหมือนที่ทำกับ `AC-x`
- เลือกระดับต่ำสุดที่พิสูจน์ได้ — boundary/decision ส่วนใหญ่เป็น unit
  แต่การถูกปฏิเสธสิทธิ์ต้องมีอย่างน้อยหนึ่ง case ที่ยิงผ่าน endpoint จริง (integration)

### 5.4 งานที่ไม่มี spec

bug, task เล็ก, โค้ดเดิมที่ไม่มีเทส → ใช้เทคนิคเดียวกันกับ **โค้ด**:
- ทุก comparison และการเช็คความยาว/จำนวน (`<`, `>=`, `.length`, `count`) = ขอบ
- ทุก branch ที่รวมเงื่อนไข ≥ 2 ตัว (AND/OR, if ซ้อน, guard หลายชั้น) = decision table
- ทุก field สถานะ/enum ที่โค้ดเปลี่ยนค่า = state transition

### 5.5 หลังเทคนิค: คิดต่อ (ห้ามข้าม)

เทคนิคหาได้เฉพาะสิ่งที่ spec หรือโค้ดเขียนไว้แล้ว ทำตารางครบแล้วให้ถามต่อ:
- ผู้ใช้จริงทำอะไรได้บ้างที่ spec ไม่ได้พูดถึง — กดซ้ำเร็ว ๆ, เปิดสองแท็บ, กด back, สองคนแก้ record เดียวกัน, ข้อมูลเก่าที่มีอยู่ก่อน migration
- ส่วนนี้ไปกระทบอะไรที่อื่น — ตัวนับ, รายงาน, dashboard, แจ้งเตือน, cache, record ที่ soft delete แล้วแต่ยังถูกนับ
- โปรเจกต์นี้เคยพังแบบไหน — task `fix`/`hotfix` ที่ปิดไปแล้วในส่วนเดียวกัน
- ข้อมูลแปลก — ไทยผสมอังกฤษ, emoji, ช่องว่างหน้า-หลัง, timezone ข้ามเที่ยงคืน

แต่ละข้อที่เป็นจริงในงานนี้ → `RK-x` พร้อมเหตุผลว่าทำไมเสี่ยง
**ไม่มีโควตาและไม่มีเพดาน** case จากขั้นนี้มีค่าเท่ากับ case จากตาราง และมักเป็นส่วนที่จับบั๊กจริงได้มากที่สุด

มากขึ้นไม่ได้แปลว่าดีขึ้น — ทุก case ยังต้องผ่านคำถามเดิม **"ถ้าลบ logic ตรงนี้ทิ้ง เทสนี้ fail ไหม"**

## 6. Integration test กับ Postman

- เก็บที่ `docs/api/postman/`
  - `<project>.postman_collection.json`
  - `local.postman_environment.json`, `uat.postman_environment.json` (**ห้ามมี secret จริง**)
- ทุก endpoint ต้องมีอย่างน้อย: happy path, validation fail, unauthorized
- ใส่ test script ใน Postman ตรวจ status + โครง response + `error.code`
- รันทั้งชุดในเครื่องด้วย newman:
  ```
  npx newman run docs/api/postman/<project>.postman_collection.json \
    -e docs/api/postman/local.postman_environment.json
  ```
- ใช้ตัวแปร collection ส่ง token ต่อระหว่าง request (login แล้วเก็บ token)
- **รันทั้งชุดก่อนขึ้น uat ทุกครั้ง**

## 7. E2E ด้วย Playwright

ทำเฉพาะเส้นทางที่ "พังแล้วธุรกิจเจ็บ":
- สมัคร / เข้าสู่ระบบ / ออกจากระบบ
- flow หลักที่สร้างรายได้หรือเป็นหัวใจของระบบ
- flow การจ่ายเงิน (ถ้ามี)

ข้อควรทำ: ใช้ `data-testid` เฉพาะจุดที่หา element ด้วย role ไม่ได้,
รันบน docker compose ที่มีข้อมูล seed คงที่, เก็บ trace ไว้ตอน fail

## 8. คำสั่งที่ต้องมี

```
pnpm test              รันทั้งหมด
pnpm test:watch        ระหว่างพัฒนา
pnpm test:cov          + coverage report (lcov + text)
pnpm test:e2e          Playwright
pnpm test:api          newman
```

`coverage/lcov.info` คือไฟล์ที่ SonarQube ใช้ — ต้อง generate ก่อน scan เสมอ
