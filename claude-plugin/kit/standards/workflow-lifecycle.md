# วงจรการทำงาน — ตั้งแต่หยิบ task จนขึ้น production

เอกสารนี้ตอบคำถามว่า **"planning เสร็จแล้วทำอะไรต่อ"** และ **"แต่ละวันทำงานยังไง"**

---

## 1. ภาพรวมวงจร

```
วางแผน (ครั้งเดียว)        วนทุกงาน                                              ปล่อยของ
──────────────────   ─────────────────────────────────────────────────    ──────────────────
Phase 1-7 ของ kit →  intent → (elaborate) → spec (ถ้าใหญ่) → plan → โค้ด → verify       →  local → uat → prd
                        ↑      → check → PR (คนกด merge หลัง gate) → done     (ปล่อยเป็นรอบ ไม่ใช่ทีละ task)
                        │      trivial: task → โค้ด → check low → PR               │
                        └────── postmortem / งานนอก scope / /insights ────────────┘

                     gate = verify + check-config + docs-lint  (pre-push และ CI ตัวเดียวกัน)
                     Phase 8: เอาบทเรียนย้อนกลับเข้า config (ทำเรื่อย ๆ)
```

**งบ context:** แต่ละขั้นอ่านอะไรได้แค่ไหน และใช้โมเดลไหน — ดู `context-budget.md` (สั้น ๆ: `/plan` อ่านครบครั้งเดียวแล้วคัดลง plan.md, ขั้นหลังจากนั้นอ่าน plan.md ไฟล์เดียว)

**หลักการของทั้งวงจร:** ทุกขั้นคายไฟล์ที่ขั้นถัดไปอ่านได้ และทุกไฟล์อยู่ใน git
ผลคือตรวจย้อนได้เสมอว่า *ใครขออะไร → ตกลงอะไรไว้ → วางแผนยังไง → ทำอะไรไป → ใครอนุมัติ*

## 1.1 งานใหม่เข้าระบบยังไง

**งานที่ต้องมีคนตัดสินใจ เข้าทาง `/intent` ทางเดียว** ไม่ว่าจะมาจากไหน
(งานที่ไม่ต้องตัดสินอะไรเลย ดูข้อ 1.2 ทางตรง):

| มาจากไหน | ทำ |
|---|---|
| ผู้ใช้เสนอ / ไอเดียใหม่ | `/intent` |
| bug ที่เจอระหว่างทาง | `/intent` (ถ้าไม่ด่วน) หรือสร้าง task ตรงถ้าเป็นของเล็กใน feature ที่มี spec แล้ว |
| ของพังบน prd | `/hotfix` ก่อน แล้ว **เปิด intent** สำหรับการแก้รากของปัญหา |
| finding จาก SonarQube / security | `/intent` ถ้าเป็นเรื่องใหญ่, task ถ้าเป็นจุดเดียว |
| feedback จาก UAT | `/intent` |

**requirement จากลูกค้าที่ให้มาคร่าว ๆ:** `/intent` จดคำของลูกค้าตามจริงและห้ามเดา จึงถามก่อนว่า brief เป็น
`open` (ให้เราคิดต่อ) หรือ `fixed` (TOR/สัญญา) · `open` → `/elaborate` หาเป้าหมายจริง research โดเมน แล้วเสนอสิ่งที่ขาด
พร้อมแหล่งที่มาลง `docs/elaboration/` ให้คนตัดสิน ข้อที่รับแล้วเท่านั้นเข้า spec · `fixed` → ข้อเสนอกลายเป็น change request

**ทำไมไม่ให้เพิ่ม task ตรง ๆ:** task ลอย ๆ ที่ไม่มีที่มา จะไม่มีใครรู้ว่าทำไมถึงทำ
พอถึงเวลาต้อง trade-off กลางทางก็ตัดสินไม่ได้ และพอจะตัดทิ้งก็ไม่มีใครกล้าตัด

### 1.2 ทางตรง — สั่งงาน AI ตรง ๆ ไม่ผ่าน skill

นอกจาก `/intent` กับ trivial track ยังมีทางที่ **คนใช้จริงบ่อยที่สุด** คือพิมพ์สั่ง AI ตรง ๆ
เอกสารชุดนี้เคยไม่พูดถึงมันเลย ผลคือทางนี้ไม่มีพื้น — ไม่มี branch ไม่มี verify ไม่มีร่องรอย
เหลือแค่ hook คอยตบตอนจะ push ซึ่งสายไปแล้วเพราะ commit ลง `main` ไปก่อนหน้านั้น

เกณฑ์ตัดสินไม่ใช่ "งานเล็กหรือใหญ่" แต่คือ 2 คำถาม ตอบตามลำดับ:

| คำถาม | ถ้า "ใช่" |
|---|---|
| มีใครต้องตัดสินใจอะไรไหม (trade-off · เปลี่ยนพฤติกรรมที่ผู้ใช้เห็น · แตะ DB / auth / สัญญา API) | `/intent` |
| อีก 3 เดือนจะมีคนย้อนถามว่า "ทำไมถึงแก้ตรงนี้" ไหม | trivial task file → `/task` |
| ไม่ใช่ทั้งคู่ | **ทางตรงได้เลย** — ไม่ต้องมี intent / task / plan |

**พื้นของทางตรง (floor) — 3 ข้อ ข้ามไม่ได้แม้จะไม่ผ่าน skill:**
1. แตก branch ก่อนแตะไฟล์แรก — ไม่แก้บน `main` ไม่ว่างานจะเล็กแค่ไหน
2. verify ผ่านก่อน commit
3. จบด้วย PR ให้คนกด — ร่องรอยของงานทางตรงคือ PR ไม่ใช่ task file

ทางตรงที่ทำครบ 3 ข้อนี้ **ไม่ใช่การลัดขั้นตอน** — มันคือขั้นตอนที่สั้นที่สุดที่ยังตรวจย้อนได้
ถ้าทำไม่ครบ แปลว่างานนั้นไม่ควรมาทางนี้ตั้งแต่แรก

> ทำไมไม่บังคับให้ทุกอย่างผ่าน skill: ด้วยเหตุผลเดียวกับที่ trivial track มีอยู่ —
> ถ้าแก้ typo ต้องเดิน 5 skill 5 รอบ คนจะเลิกใช้ระบบทั้งระบบ นั่นคือวิธีที่ process ตายจริง ๆ

## 2. สถานะของงานบนกระดาน

| สถานะ | หมายถึง | ใครย้าย | เงื่อนไขย้ายออก |
|---|---|---|---|
| `backlog` | ยังไม่ถึงคิว | คน | จัดเข้า milestone แล้ว |
| `todo` | พร้อมทำ dependency ครบแล้ว | คน | มีคนหยิบ |
| `in-progress` | กำลังทำ | AI (ตอนเริ่ม) | โค้ดเสร็จ + self-check ผ่าน |
| `review` | รอตรวจ / PR เปิดแล้ว | AI (ตอนเสร็จ) | ผ่าน `/check` + คนกด merge PR หลัง gate ผ่าน |
| `done` | PR merge แล้ว มี `commit:` | `/done` หลังคนกด merge | — |
| `blocked` | ติดอะไรบางอย่าง | ใครก็ได้ | **ต้องระบุเหตุผลและสิ่งที่รอ** |

**กฎ WIP:** `in-progress` ได้ทีละ **1 task ต่อคน** เท่านั้น
เหตุผล: เขียนโค้ดด้วย AI ทำหลาย task พร้อมกันแล้ว context ปนกัน โค้ดจะขัดกันเอง

## 3. รอบการทำงานหนึ่ง task (ทำซ้ำทุกวัน)

### 3.1 หยิบงาน — `/task`
Claude จะ:
1. อ่าน `docs/backlog/board.md`
2. เลือก task ที่ `todo` ลำดับบนสุดที่ dependency ครบ (หรือทำตามที่ผู้ใช้ระบุ)
3. อ่านไฟล์ task + spec ที่เกี่ยว
4. **สรุปความเข้าใจให้ฟังก่อน แล้วถามสิ่งที่ไม่ชัด** ← อย่าข้ามขั้นนี้
5. เมื่อผู้ใช้ยืนยัน → สร้าง branch → ย้ายสถานะเป็น `in-progress`

### 3.1b วางแผน — `/plan <T-xxx>`

**ต้องทำ** ถ้างานเข้าข้อใดข้อหนึ่ง: แตะเกิน 3 ไฟล์ / แตะ DB / แตะ auth /
แก้ของเดิมที่มีคนใช้อยู่ / ไม่คุ้นโค้ดส่วนนั้น

**ข้ามได้** ถ้าอธิบาย diff ทั้งหมดได้จบใน 1 ประโยค (แก้ typo, เพิ่ม log)

ทำใน **plan mode** (กด `Shift+Tab` — Claude แก้ไฟล์ไม่ได้ทางเทคนิค) แล้ว commit
`docs/plans/<T-xxx>.md` ก่อนเริ่มเขียนโค้ด ไฟล์ต้องมีครบ 4 อย่าง:
**ไฟล์ที่จะเปลี่ยน / ลำดับงาน / ความเสี่ยง / Proof ว่าอะไรพิสูจน์ว่าเสร็จ**

> เหตุผล: การเจอปัญหาตอนที่ยังเป็นเอกสาร ถูกกว่าการเจอตอนโค้ดเสร็จแล้วมาก
> และ `plan.md` จะถูกใช้เทียบกับ diff ตอนรีวิว — ส่วนต่างที่อธิบายไม่ได้คือสัญญาณว่างานหลุด scope

### 3.2 เขียนโค้ด
- ทำตาม acceptance criteria ทีละข้อ
- ถ้าต้องสร้าง UI component → **ใช้ `/ui` และตอบคำถามก่อนเสมอ** (ดู `ui-component-rules.md`)
- ถ้าเจอสิ่งนอก scope → **หยุดถาม** อย่าทำเผื่อ แล้วเปิด task ใหม่แทน
- commit ย่อยระหว่างทางได้ ตาม Conventional Commits

### 3.3 ตรวจตัวเอง (ก่อนขอ review)
รันจริง **แล้วแปะผลลัพธ์จริงให้ดู** ห้ามรายงานว่าผ่านถ้ายังไม่ได้รัน:
```
node .claude/verify.js
```
แล้วทำ **Proof** ที่เขียนไว้ในแผนให้ครบและแสดงผล จากนั้นเทียบกับ Definition of Done ของประเภทงานนั้น

> การประกาศว่า "เรียบร้อยแล้ว" โดยไม่มีหลักฐาน คือช่องโหว่ที่แพงที่สุดของการเขียนโค้ดด้วย AI
> ถ้ากฎข้อนี้หลวมเมื่อไหร่ ทุกอย่างที่เหลือในระบบก็เชื่อไม่ได้ทั้งหมด

### 3.4 ตรวจ — `/check`
- รัน verify (แปะบรรทัดสรุป) → เทียบ diff กับ **plan.md ไฟล์เดียว** → built-in `/code-review` (+ `/security-review` ถ้าแตะ auth/api/db) → subagent `code-reviewer` ตรวจกติกาโปรเจกต์
- รายงาน**เฉพาะข้อที่ไม่ผ่าน** ส่งผลของ built-in/subagent ผ่านตามที่มันเขียน
- **คนเป็นผู้อนุมัติเสมอ** AI ไม่อนุมัติงานตัวเอง

### 3.5 ปิดงาน — `/done`
Claude จะ: อัปเดตไฟล์ task → `git push` + **เปิด PR** (hook บล็อก merge เอง) → **คนกด merge** หลัง gate (pre-push/CI) ผ่าน →
`status: done` + `commit:` → ปลดล็อก task ที่รอ (รวม `-test`) → `node .claude/board.js` → ป้อนบทเรียนเข้า config → บอกให้ `/clear`

> ทำงานคนเดียว: คุณกด merge เองใน UI หลังอ่านสรุป ใช้ 10 วินาที แต่ได้ประวัติว่าใครอนุมัติ และ gate ได้รันจริง
> ทำงานหลายคน: เพิ่ม reviewer ใน PR — flow เดียวกัน

### 3.0 trivial track
งาน typo / copy / log / chore ที่อธิบาย diff ได้ใน 1 ประโยค: สร้างไฟล์ task ตรง (`track: trivial`, "ทำไม" 1 บรรทัด) → `/task` → `/check` (low) → PR
ไม่ต้อง intent / plan — ถ้าทุกงานต้องผ่าน 5 skill คนจะเลิกใช้ระบบทั้งชุด

## 4. ประเภทงานและวิธีคุมที่ต่างกัน

### 4.1 Feature ใหญ่ (epic / feature ใหม่)
```
/spec <F-xx>  →  requirements.md → design.md → tasks.md  →  ผู้ใช้อนุมัติ  →  แตกเป็น task  →  ทำทีละ task
```
- spec เก็บที่ `docs/specs/<feature>/`
- **ต้องอนุมัติ spec ก่อนเขียนโค้ด** ห้ามข้าม
- ถ้าระหว่างทำแล้ว design เปลี่ยน → **แก้ spec ก่อน แล้วค่อยแก้โค้ด** (ไม่งั้น spec จะโกหกทันที)

### 4.2 Task ย่อย (งานเล็กใน feature ที่มี spec แล้ว)
- ไม่ต้องทำ spec ใหม่ ใช้ไฟล์ task + acceptance criteria พอ
- อ้างอิง spec ของ feature แม่

### 4.3 แก้ feature เดิม
1. อ่าน spec เดิม + โค้ดเดิมก่อน **ห้ามแก้แบบไม่อ่านของเดิม**
2. ประเมิน **ผลกระทบ**: ใครเรียกใช้บ้าง, กระทบ API contract ไหม, กระทบ DB ไหม
3. ถ้ากระทบ API → เป็น breaking change ต้องคุยเรื่อง version
4. อัปเดต spec + test + OpenAPI ไปพร้อมกัน
5. commit ใช้ `feat:` (ถ้าเพิ่มพฤติกรรม) หรือ `refactor:` (ถ้าไม่เปลี่ยนพฤติกรรม)

### 4.4 Bug ปกติ
1. **เขียน test ที่ fail ก่อน** (พิสูจน์ว่าเจอบั๊กจริง)
2. แก้ให้ test ผ่าน
3. commit `fix:` และอ้าง task id
4. ถามตัวเองว่า "ที่อื่นมีแบบเดียวกันไหม" ถ้ามีให้เปิด task

### 4.5 Hotfix (ของพังบน production)
```
/hotfix
```
ลำดับที่ต้องทำ:
1. **บันทึกอาการก่อน** — อะไรพัง ใครกระทบ ตั้งแต่เมื่อไหร่ (เขียนลงไฟล์ก่อนแก้)
2. แตก branch จาก **สิ่งที่อยู่บน prd ตอนนี้** ไม่ใช่จาก main ที่มีของใหม่ปนอยู่
3. แก้ให้ **เล็กที่สุดเท่าที่จะหยุดเลือดได้** ห้าม refactor ระหว่าง hotfix
4. เขียน test ที่ครอบบั๊กนั้น
5. ทดสอบบน local → uat (ถ้าเวลาพอ) → prd
6. **merge กลับ main ทันที** กันบั๊กย้อนกลับมาในรอบหน้า
7. หลังไฟดับแล้ว → เขียน **postmortem สั้นๆ** (สาเหตุ, ทำไมหลุด, จะกันยังไง) + เปิด task ถาวร

### 4.6 Refactor / งานเทคนิค
- ต้องมี test คลุมก่อนเริ่ม ถ้าไม่มีให้เขียนก่อน
- **ห้ามเปลี่ยนพฤติกรรมและ refactor ใน commit เดียวกัน**
- commit `refactor:`

## 5. ปรับแผนกลางทาง (เกิดขึ้นบ่อย ต้องมีวิธี)

เปลี่ยนอะไรก็ได้ระหว่างทาง แต่ต้อง **อัปเดตเอกสารต้นทางเสมอ** ไม่ใช่แก้แต่โค้ด:

| เปลี่ยนอะไร | ต้องอัปเดตอะไรตาม |
|---|---|
| เพิ่ม/ลด feature | `01-requirements.md` (MoSCoW) → board → task |
| เปลี่ยน UI | `docs/design/` → spec ของ feature → task |
| เปลี่ยนสถาปัตยกรรม | **ADR ใหม่ที่ supersede อันเดิม** → `04-architecture.md` |
| เปลี่ยนลำดับงาน | `board.md` + `05-roadmap.md` |
| เพิ่ม task จาก dashboard ภายนอก | สร้างไฟล์ `docs/backlog/tasks/T-xxx.md` ให้ AI มองเห็น |

**กฎเหล็ก:** ถ้าโค้ดกับเอกสารไม่ตรงกัน แปลว่ามีอย่างหนึ่งผิด — ต้องแก้ให้ตรงกันในรอบนั้นเลย
เพราะ AI อ่านเอกสารเป็นความจริง ถ้าเอกสารโกหก AI จะเขียนโค้ดผิดต่อเนื่อง

## 6. การปล่อยของ: local → uat → prd

### 6.1 หลักการ
- **artifact เดียวกันไหลผ่านทุก env** build image ครั้งเดียว เปลี่ยนแค่ env var
  (ห้าม build ใหม่ตอนขึ้น prd — ของที่เทสบน uat จะไม่ใช่ของที่ขึ้นจริง)
- ปล่อยเป็น **รอบ** ตาม milestone ไม่ใช่ปล่อยทีละ task

### 6.2 local
- `docker compose -f docker-compose.dev.yml up -d`
- ข้อมูล seed, บัญชีทดสอบทุก role, mailpit รับอีเมลแทนการส่งจริง

### 6.3 ขึ้น uat
ก่อนขึ้นต้องผ่าน:
- [ ] ทุก task ในรอบเป็น `done`
- [ ] `build` / `lint` / `typecheck` / `test` ผ่าน
- [ ] รัน SonarQube local แล้วผ่าน quality gate
- [ ] รัน Postman collection ผ่าน
- [ ] migration รันบน DB สำเนาของ uat ได้ (และมีแผน rollback)
- [ ] อัปเดต `docs/api/openapi.json` แล้ว
- [ ] เขียน release note: มีอะไรใหม่ / แก้อะไร / ต้องทดสอบอะไร

บน uat ทำอะไร: ให้คนทดสอบจริงตาม release note, เก็บ bug เป็น task ใหม่,
ทดสอบ i18n ทั้งสองภาษา, ทดสอบบนมือถือจริง

### 6.4 ขึ้น prd
ก่อนขึ้นต้องผ่านทุกข้อของ uat **บวก**:
- [ ] UAT อนุมัติแล้วเป็นลายลักษณ์อักษร
- [ ] security checklist ผ่าน (`security-checklist.md`)
- [ ] **backup ฐานข้อมูลก่อนรัน migration** และซ้อม restore มาแล้ว
- [ ] env var ของ prd ครบและ secret ไม่ได้อยู่ใน git
- [ ] มี **แผน rollback** ที่ทำได้จริงภายในกี่นาที
- [ ] `/health` `/ready` ตอบถูกต้อง
- [ ] ปิด/ป้องกันหน้า `/docs` และ debug endpoint
- [ ] ตกลงเวลาปล่อย + ใครเฝ้าหลังปล่อย

หลังปล่อย: เฝ้า log/error 30–60 นาที, ทดสอบ flow หลักด้วยตัวเอง,
ติด **tag** เวอร์ชัน (`v1.2.0`) และเขียน CHANGELOG

### 6.5 Rollback
เตรียมคำตอบไว้ล่วงหน้า 2 ข้อ:
1. **โค้ด** — กลับไป image tag ก่อนหน้าได้ภายในกี่นาที
2. **ฐานข้อมูล** — migration รอบนี้ย้อนกลับได้ไหม
   ถ้าย้อนไม่ได้ (เช่น drop column) → **ต้องทำแบบ expand/contract**:
   รอบที่ 1 เพิ่มของใหม่โดยของเก่ายังอยู่ → ปล่อย → รอบถัดไปค่อยลบของเก่า

## 7. จังหวะประจำ (แม้ทำคนเดียวก็ควรมี)

| เมื่อไหร่ | ทำอะไร |
|---|---|
| เริ่มวัน | ดู board (hook ฉีดให้อัตโนมัติแล้ว), เลือก task, ยืนยันความเข้าใจกับ AI |
| จบ task | review → done → อัปเดต board → **ถามว่ามีบทเรียนอะไรควรเข้า config ไหม** |
| จบสัปดาห์ | รัน Sonar, ดู coverage, เก็บกวาด `blocked` และ intent ที่ค้าง, ปรับลำดับ backlog |
| จบ milestone | demo, `/release`, ทบทวนว่าอะไรช้ากว่าคิด, **ทำ Phase 8 เต็มรูปแบบ** |
| หลัง incident | postmortem → intent สำหรับแก้ราก → **เขียน eval** ทันที ห้ามรอรอบ |

## 8. ป้อนบทเรียนกลับเข้า config (สิ่งที่ทำให้ระบบเรียนรู้)

ถ้าไม่ทำข้อนี้ ระบบจะทำผิดเรื่องเดิมไปเรื่อย ๆ ตลอดอายุโปรเจกต์:

```
พลาดครั้งแรก          → แก้ในเทิร์นนั้น ไม่ต้องทำอะไรเพิ่ม
พลาดครั้งที่ 2         → เขียนลง AGENTS.md หมวด "สิ่งที่ AI ในโปรเจกต์นี้เคยทำผิด"
พลาดซ้ำแม้เขียนไว้แล้ว  → เลื่อนชั้นเป็น rule ที่ผูก paths
พังแล้วเจ็บจริง        → hook (บังคับ) + eval (กันถอยหลัง)
```

รายละเอียดวิธีเขียนแต่ละชั้น: `docs/standards/agent-config.md`
