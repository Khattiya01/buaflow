# Security baseline: threat boundary + control set ภายนอก (EP-003)

`standards/deployment-ready-contract.md` บอกไว้ตั้งแต่วันที่เขียน R0–R4 ว่า control
`security-controls` ต้องการ **"threat boundary + applicable ASVS/control proof"**
แต่คำว่า ASVS ปรากฏอยู่แค่สองไฟล์ในเรพทั้งหมด — ในเอกสารนั้นเองกับใน roadmap — และไม่มีอะไร
ผลิตหรือตรวจ mapping นั้นเลย ผลคือ control ที่**บังคับที่ R3** ถูกทำให้ผ่านด้วยย่อหน้าใน
`docs/security-notes.md`

## ทำไมต้องเป็น control set ของคนอื่น

`standards/security-checklist.md` เป็น checklist ที่เขียนขึ้นเองที่นี่ อิง OWASP Top 10
ปรับให้เข้ากับ TypeScript + Node + Prisma — มีประโยชน์สำหรับ review รายวัน แต่ใช้เป็นฐานของ
คำว่า "ปลอดภัยตามมาตรฐาน" ไม่ได้ เพราะ**เราเป็นคนเลือกเองว่าจะใส่ข้อไหน** checklist ที่เจ้าของ
โปรเจกต์เขียนเองแล้วให้คะแนนตัวเองผ่าน คือปัญหาเดียวกับ north-star metric ที่มีตัวหารเป็น
reference app ของตัวเอง

`standards/control-sets/owasp-asvs-5.0.0-l1.json` จึงเป็น **สำเนา** ไม่ใช่งานเขียน:

| ฟิลด์ | ค่า |

## สัญญา

ไฟล์ `docs/evidence/security-baseline.json` (`schemas/security-baseline.schema.json`)
ตรวจด้วย `node .claude/security-baseline.js` หรือ `buaflow security`

### 1. threat boundary เป็นข้อมูล ไม่ใช่ย่อหน้า

แต่ละ boundary บอกว่า **อะไรไม่เชื่อถือ / อะไรอยู่ด้านใน / ของมีค่าคืออะไร / เข้ามาทางไฟล์ไหน /
ไฟล์ไหนบังคับกฎ** และไฟล์ที่อ้างถึงต้องมีอยู่จริง — boundary ที่ชี้ไปโค้ดที่ถูกลบไปแล้วคือคำอธิบาย
ของระบบที่ไม่มีอยู่อีกต่อไป ซึ่งอันตรายกว่าไม่เขียนไว้เลย

### 2. ทุก control ต้องมีคำตอบ

| status | ต้องมี |
|---|---|
| `met` | หลักฐานที่ทำซ้ำได้ — manual ล้วนไม่นับ (กติกาเดียวกับ EP-002) |
| `not-met` | **`exception` ที่ชี้ไป requirement ใน `requirement-coverage.json` ที่มี exception จริง** |
| `not-applicable` | เหตุผลเฉพาะโปรเจกต์อย่างน้อย 20 ตัวอักษร |

control ที่หายไปเฉย ๆ = ตก และตัวตรวจจะบอกว่าข้อไหนหาย — ไม่งั้นมันไม่ใช่ baseline
แต่เป็นรายการที่เลือกมาเฉพาะข้อที่ผ่าน

บทที่ใช้ไม่ได้ทั้งบท `exclude` ได้ทีเดียวพร้อมเหตุผล เพื่อไม่ให้ baseline กลายเป็น 70 บรรทัดที่
เขียนว่า not-applicable เหมือนกันหมด แต่ `exclude` แล้วห้ามตอบรายข้อในบทนั้นอีก

### 3. control ที่ไม่ผ่านต้องมีเจ้าของและวันหมดอายุ

ข้อนี้คือหัวใจ และเป็นเหตุผลที่ EP-003 ไม่สร้างทะเบียนความเสี่ยงชุดที่สอง: `not-met` ต้องชี้ไป
approved exception ของ EP-002 ที่มีอยู่จริง แปลว่า

- ช่องโหว่ที่ยอมรับแล้วมี**ที่อยู่ที่เดียว**ในโปรเจกต์
- `--max-window-days` ของ EP-002 ทำให้มันหมดอายุ — ไม่มีแถวสีแดงที่อยู่เฉย ๆ ตลอดกาล
- การชี้ไป requirement ที่ **พิสูจน์แล้ว** (ไม่ใช่ exception) ถูกปฏิเสธ ไม่งั้น requirement ที่ผ่าน
  จะถูกใช้ฟอกให้ control ที่ไม่ผ่านดูเหมือนมีคนรับผิดชอบ

## สิ่งที่การทำ baseline ครั้งแรกเจอจริง

การ map ครั้งแรกกับ reference app สามตัว (2026-09-23) ทำให้เห็น 7 ช่องที่
`docs/security-notes.md` ไม่เคยเขียนถึง เพราะ prose บอกได้แค่ว่าแอป**ทำอะไร** ไม่เคยบอกว่า
**ไม่ได้ทำอะไร**:

| ที่เจอ | ASVS | ความเสี่ยงที่บันทึก |
|---|---|---|
| logout ลบ cookie แต่ token ที่ถูกดักไว้ยังใช้ได้จนหมดอายุ 8 ชั่วโมง | V7.2.4, V7.4.1 | **high** (REQ-104) |
| บัญชี seed ที่รหัสผ่านอยู่ในเรพ | V6.3.2 | **high** (REQ-106) |
| ไม่มี security header เลย และไม่ล้างข้อมูลฝั่ง client ตอนจบ session | V3.2.1, V14.3.1 | medium (REQ-102) |
| TLS/HSTS ฝากไว้กับ edge ที่ไม่ได้ ship | V3.4.1, V12.x | medium (REQ-101) |
| ไม่มีฟังก์ชันเปลี่ยนรหัสผ่าน | V6.2.2 | medium (REQ-105) |
| SPA fallback ประกอบ path จาก request โดยไม่มีเทสยืนยัน | V5.3.2 | medium (REQ-108) |
| cookie ไม่มี `__Host-`/`__Secure-` prefix | V3.3.1 | low (REQ-103) |
| ไม่มีเอกสารกำหนดเวลาที่ต้องเปลี่ยน dependency ที่มีช่องโหว่ | V15.1.1 | low (REQ-107) |

ทั้งหมดถูกบันทึกเป็น exception ที่มีเจ้าของและหมดอายุ **2026-12-22** ไม่ใช่ถูกแก้ — นั่นคือ
การตัดสินใจของเจ้าของโปรเจกต์ที่บันทึกไว้ ไม่ใช่ค่าเริ่มต้นที่เงียบ ๆ

> ข้อที่ควรอ่านซ้ำ: **30 met, 16 not-applicable, 15–16 not-met** คือหน้าตาจริงของแอปที่ผ่าน R3
> ครบทุก control อยู่แล้ว การมี baseline ไม่ได้ทำให้แอปแย่ลง มันทำให้สิ่งที่เป็นจริงอยู่แล้วมองเห็นได้

## additive

โปรเจกต์ที่ไม่มี `docs/evidence/security-baseline.json` ไม่ถูกตรวจข้อนี้เลย และ `gate.js`
ไม่เปลี่ยนพฤติกรรมใด ๆ — นี่คือเหตุผลที่ 3.2.0 เป็น MINOR ตาม `standards/release-policy.md`

## เปลี่ยนไปใช้ control set อื่นหรือเวอร์ชันใหม่

`controlSet` เป็นชื่อไฟล์ใน `standards/control-sets/` — เพิ่มไฟล์ใหม่แล้วชี้ไปที่มันได้เลย
การอัปเดตเป็น ASVS เวอร์ชันถัดไปคือการเพิ่มไฟล์ใหม่ ไม่ใช่การแก้ไฟล์เดิม เพราะ baseline เก่า
ต้องยังอ่านได้ว่ามันถูกตัดสินด้วยมาตรฐานฉบับไหน
