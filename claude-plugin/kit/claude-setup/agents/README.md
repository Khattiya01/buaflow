# ทำไมมี subagent แค่ 3 ตัว

## ลำดับชั้นของการบอกให้ AI ทำอะไร

เครื่องมือแต่ละอย่างแก้ปัญหาคนละแบบ เลือกผิดชั้น = เปลืองทั้ง context และแรง:

| ต้องการอะไร | ใช้อะไร | โหลดเมื่อไหร่ | แข็งแค่ไหน |
|---|---|---|---|
| ความรู้ที่ต้องรู้ตลอด | `AGENTS.md` (Claude อ่านผ่าน `CLAUDE.md`) | ทุก session | แนะนำ |
| ข้อบังคับเฉพาะโซนไฟล์ | `.claude/rules/*.md` + `paths:` | เมื่อแตะไฟล์ที่ match | แนะนำ |
| ขั้นตอนที่ทำซ้ำ / ความรู้ที่ใช้เป็นบางครั้ง | `.claude/skills/<ชื่อ>/SKILL.md` | เมื่อถูกเรียก หรือเมื่อ Claude เห็นว่าเกี่ยว | แนะนำ |
| **กฎที่ห้ามพังเด็ดขาด** | `.claude/hooks/` + `settings.json` | ทุกครั้งที่ event ตรง | **บังคับจริง** |
| **แยก context** | `.claude/agents/<ชื่อ>.md` | เมื่อถูก delegate | — |

กฎง่าย ๆ:
- เขียนไว้ใน `AGENTS.md` แล้วยังพลาดซ้ำ → เลื่อนชั้นเป็น rule หรือ hook
- ขั้นตอนยาวเกิน ~30 บรรทัดใน `AGENTS.md` → ย้ายไปเป็น skill
- rule ที่ไม่มี `paths:` → กิน context ทุก session ทั้งที่ไม่เกี่ยว ให้ scope เสมอ

## ทำไมไม่เขียน agent ตามตำแหน่งงาน

**การเขียน agent เป็น full-stack / QA / PM / DevOps / architect ไม่ช่วยอะไร**
เพราะ Claude ตัวหลักทำได้ทั้งหมดอยู่แล้ว การแยกเป็น "ตำแหน่ง" มีแต่ทำให้
context กระจัดกระจายและต้องคอยส่งข้อมูลข้ามกันไปมา

มีเฟรมเวิร์กที่ทำแบบนั้น (จำลองทีม agile ทั้งทีมด้วย agent หลายบทบาท)
เราตั้งใจ **ไม่ทำตาม** เพราะมันเพิ่มชั้นการประสานงานโดยไม่ได้เพิ่มคุณภาพผลลัพธ์
สิ่งที่ทำให้ผลลัพธ์ดีขึ้นจริงคือ **artifact ที่ต่อกันเป็นทอด** และ **กฎที่บังคับได้**
ไม่ใช่จำนวนบทบาทที่จำลองขึ้นมา

## subagent คุ้มเมื่อไหร่

เมื่อ **งานนั้นต้องอ่านของเยอะแต่ส่งกลับมานิดเดียว** ซึ่งมี 3 กรณีในโปรเจกต์นี้:

| agent | แยก context เพราะ |
|---|---|
| `code-reviewer` | ต้องอ่าน diff ทั้งก้อนแบบเป็นกลาง โดยไม่ถูก "ความทรงจำว่าเพิ่งเขียนอะไรไป" ครอบงำ — context ที่สะอาดคือเหตุผลหลักที่มันเจอสิ่งที่คนเขียนมองข้าม |
| `test-writer` | ต้องอ่านโค้ดและเทสเดิมเยอะ แต่ผลลัพธ์คือไฟล์เทสไม่กี่ไฟล์ |
| `legacy-explorer` | โค้ดโปรเจกต์เก่าใหญ่มาก ถ้าอ่านใน context หลักจะบวมจนงานหลักเสียคุณภาพ |

ส่วนงานค้นหาทั่วไปให้ใช้ **Explore** ที่มีมาให้อยู่แล้ว ไม่ต้องเขียนเอง

## ถ้าอยากเพิ่ม agent ทีหลัง

ถามตามลำดับนี้:

1. **เป็นกฎที่ห้ามละเมิดไหม** → hook
2. **เป็นกฎที่ผูกกับไฟล์บางกลุ่มไหม** → rule + `paths:`
3. **เป็นขั้นตอนที่ต้องอธิบายซ้ำทุกครั้งไหม** → skill
4. **ทำให้ context หลักบวมโดยไม่จำเป็นไหม** → subagent
5. ถ้าไม่เข้าข้อไหนเลย → อาจไม่ต้องมีอะไรเลย
