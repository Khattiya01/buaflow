# หมวดความล้มเหลว (EV-003)

มาตรฐานนี้กำหนดชุดหมวดที่ใช้เรียกความล้มเหลว เพื่อให้ "เกิดอะไรขึ้น" เทียบข้ามโปรเจกต์และข้ามเวลาได้
โดยไม่ต้องอาศัยการเล่าเรื่องใหม่ทุกครั้ง

**ฐานข้อมูลคือของจริง ไม่ใช่หมวดหมู่ที่ลอกมา** — taxonomy เป็นงานที่ลอกจากตำรามาได้ง่ายมาก
แล้วได้ของที่สวยแต่ไม่มีใครใช้ ที่นี่จึงมีกติกาข้อเดียวที่บังคับด้วยเครื่อง:
**ทุกหมวดต้องชี้ไปที่ความล้มเหลวที่เกิดขึ้นจริงในเรพนี้ พร้อมที่อยู่ที่ตรวจกลับได้**
`claude-setup/tests/failure-taxonomy.test.js` ตรวจว่า citation ทุกอันมีอยู่จริง —
work item และ decision ต้องมีใน `state.json` ส่วน path ต้องมีอยู่บนดิสก์

## หมวดทั้งหมด

| หมวด | ความหมาย | เคสจริงที่ทำให้หมวดนี้มีอยู่ |
|---|---|---|
| `spec-gap` | สัญญาไม่ได้พูดถึงสิ่งที่มันควรกำกับ จึงไม่มีอะไรผิดได้ | `generatedArtifacts` ของ pack v1 บรรยายไฟล์ที่ generator จะเขียน ทั้งที่ไม่มี generator อยู่จริง |
| `contract-drift` | artifact สองอันที่ควรตรงกัน เลิกตรงกัน และไม่มีอะไรเทียบ | pack `nextjs-postgres` ประกาศ `.claude/stack.json` ที่ reference app ไม่เคยมี |
| `implementation-defect` | โค้ด compile ผ่าน type ผ่าน review ผ่าน แต่ทำงานผิดตอนรัน | sync ที่ทำงานหลัง mutation อ่าน state เก่าแล้วเขียนทับการแก้ที่เพิ่งทำ — data loss จริง |
| `integration-mismatch` | แต่ละชิ้นถูกหมด แต่ประกอบกันแล้วพัง มักที่ขอบ platform/module | branch ด้วย `Platform.OS` ตอน runtime ยังดึง WASM worker ของ expo-sqlite เข้า web bundle แบบ static |
| `supply-chain-finding` | dependency ที่ไม่เคยเลือกเองพาความเสี่ยงมาด้วย | uuid advisory ที่มาทาง iOS tooling chain ของ Expo เอง 10 รายการ |
| `toolchain-failure` | เครื่องมือ build/CI พังด้วยเหตุที่ไม่เกี่ยวกับโค้ดเลย | `setup-android@v3` ขอ SDK package ชื่อ `tools` ที่ Google เอาออกไปหลายปีแล้ว |
| `verification-gap` | ตัวตรวจที่ควรจับได้ ไม่มีอยู่ หรือมีแต่ไม่เคยรัน | `npm run check` มีครบแต่ไม่มี workflow ไหนรัน · command evidence ไม่เคยถูกรันซ้ำเลย |
| `evidence-defect` | ตัวหลักฐานเองหาย ว่าง เก่า หรือถูกทำลาย จน claim ที่จริงกลายเป็นพิสูจน์ไม่ได้ | verifier รัน `--execute` แล้วเขียนทับ `playwright-report.json` ทำลายหลักฐาน R3 ไป 238 บรรทัด |
| `guidance-defect` | คำสั่งที่ทำตามได้ แต่จะพาคนถัดไปไปที่ที่แย่กว่าเดิม | recipe ของ `auth-rbac` สั่งลง `iron-session` + `bcrypt` ที่ implementation จริงตั้งใจไม่ใช้ |

ดูรายละเอียดเต็มพร้อม "อะไรจับมันได้": `node .claude/failure-taxonomy.js --list`

## ช่องว่างที่ประกาศไว้ ไม่ใช่ลืม

**ไม่มีหมวด `operations-failure`** เพราะเรพนี้ยังไม่เคยรันอะไรใน production จึงไม่มีเหตุการณ์จริงให้ยึด
การเติมหมวดนี้จากรายการหมวดหมู่ คือความล้มเหลวแบบ "taxonomy ที่ลอกมา" ที่มาตรฐานนี้มีไว้กันพอดี

ช่องว่างนี้ปิดได้เมื่อ **EV-009** เกิดขึ้น (trial บนโปรเจกต์ที่ Buaflow ไม่ได้เขียนเอง) และ test บังคับไว้ว่า
ห้ามเติมหมวดนี้โดยไม่มีของจริงรองรับ

> ช่องว่างที่ประกาศไว้มีค่ามากกว่า taxonomy ที่ดูครบ — มันบอกว่าเรายังไม่รู้อะไร

## `detectedBy` คือคอลัมน์ที่มีค่าที่สุด

ทุก failure record **บังคับ** ให้ตอบว่าอะไรเป็นคนจับได้ และ **"ไม่มีอะไรจับได้" เป็นคำตอบที่ใช้ได้
และมีค่าที่สุด** เพราะมันชี้ช่องที่ยังว่าง

เทียบกับของจริงในเรพนี้:

- `contract-drift` ถูกจับโดย binding check **ตั้งแต่รันครั้งแรก** → gate นั้นคุ้มค่า
- `implementation-defect` ถูกจับโดย e2e test ที่ล้มจริง หลังแก้ผิดไปสองรอบ → test คุ้มค่า
- `spec-gap` ถูกจับโดย **คนอ่านสัญญา ไม่มีเครื่องมือไหนจับ** → ช่องที่ยังว่าง
- `evidence-defect` ถูกจับโดย `git status` **หลังเกิดเหตุแล้ว** → ช่องที่ยังว่าง

สองบรรทัดล่างคือรายการงานที่มาจากข้อมูล ไม่ใช่จากการเดา

## failure record

เก็บที่ `docs/evidence/failures/F-00x.json` ตาม `schemas/failure-record.schema.json`

```bash
node .claude/failure-taxonomy.js --list                       # ดูหมวดทั้งหมด
node .claude/failure-taxonomy.js --dir docs/evidence/failures # ตรวจทุก record
```

`class` ที่ไม่มีอยู่จริงจะถูกปฏิเสธ — นี่คือสิ่งที่ทำให้ taxonomy เป็นสัญญา ไม่ใช่คำแนะนำ

## กติกาการเพิ่มหมวด

1. ต้องมีเหตุการณ์จริงอย่างน้อยหนึ่งเคส พร้อม citation ที่ตรวจกลับได้
2. ต้องต่างจากหมวดที่มีอยู่จริง ไม่ใช่ชื่อใหม่ของเรื่องเดิม
3. ต้องตอบได้ว่าอะไรจับมันได้ หรือประกาศว่าไม่มีอะไรจับ
4. ถ้ายังไม่มีเคสจริง **ให้ประกาศเป็น known gap แทน** ตามแบบของ `operations-failure`
