# นโยบายเวอร์ชันและความเข้ากันได้ของ kit (EV-007)

`standards/artifact-versioning.md` กำหนดกติกาของ **artifact** ที่ Buaflow เป็นเจ้าของ
เอกสารนี้กำหนดกติกาของ **ตัว kit เอง** — สิ่งที่ผู้ใช้คัดลอกเข้าโปรเจกต์ตัวเองใน Phase 7

> ก่อนหน้า v3.0.0 เลขเวอร์ชันของ kit ไม่ได้แปลว่าอะไรเลย `package.json` บอก `2.3.4` โดยไม่มีสัญญา
> รองรับ ผู้ใช้ที่คัดลอก `claude-setup/` เข้าโปรเจกต์จึงไม่มีทางรู้ว่าอัปเกรดแล้วจะพังตรงไหน

## เลขแต่ละหลักแปลว่าอะไร — นิยามจากมุมผู้ใช้ ไม่ใช่มุมคนเขียน

| หลัก | เกิดเมื่อ | ผู้ใช้ต้องทำอะไร |
|---|---|---|
| **MAJOR** | อัปเกรดแล้ว**ผู้ใช้ต้องลงมือแก้อะไรบางอย่าง** จึงจะกลับมาทำงานได้ | อ่าน `UPGRADE.md` แล้วแก้ตามขั้นตอน |
| **MINOR** | มีความสามารถเพิ่ม โดยของเดิมยังทำงานเหมือนเดิมทุกอย่าง | คัดลอกไฟล์ทับ จบ |
| **PATCH** | แก้บั๊ก/แก้ถ้อยคำ ไม่มีพฤติกรรมสาธารณะเปลี่ยน | คัดลอกไฟล์ทับ หรือข้ามไปก็ได้ |

สิ่งที่นับเป็น **MAJOR** ชัดเจน:

- artifact schema ขึ้น major และ migration เป็น `manual` (ผู้ใช้ต้องเขียนไฟล์ใหม่เอง)
- ลบหรือเปลี่ยนชื่อ readiness control, control id หรือ exit code ของ CLI
- เปลี่ยนความหมายของ field เดิม แม้ชื่อจะเหมือนเดิม
- ทำให้ gate ที่เคยผ่านกลายเป็นไม่ผ่านโดยที่โปรเจกต์ไม่ได้เปลี่ยนอะไร

> **เกณฑ์ตัดสินข้อเดียว: ถ้าผู้ใช้ต้องลงมือ มันคือ MAJOR** ไม่ว่าการเปลี่ยนแปลงจะดูเล็กแค่ไหนในสายตาคนเขียน

## Support matrix อยู่ในไฟล์ข้อมูล ไม่ใช่ในเอกสารนี้

`schemas/compatibility.json` บอกว่า kit แต่ละรุ่นอ่าน artifact schema เวอร์ชันไหนได้บ้าง
ตามหลักการข้อ 2 ของ roadmap (Markdown เป็นมุมมอง ไม่ใช่ฐานข้อมูล) — เอกสารนี้อธิบาย ไฟล์นั้นเป็นความจริง

`scripts/check-compatibility.js` ทำให้มันโกหกไม่ได้ และรันอยู่ใน `npm run check` (จึงอยู่ใน CI):

- `package.json` version ต้องตรงกับรีลีสบนสุดของ matrix
- artifact type ที่ `schemas/registry.json` ประกาศเป็น public **ทุกตัว** ต้องอยู่ใน matrix
- เวอร์ชัน `latestVersion` ของแต่ละ type ต้องอยู่ในรายการที่รีลีสล่าสุดบอกว่าอ่านได้
- type ที่อยู่ใน matrix แต่ registry ไม่รู้จัก = ผิด
- รีลีสต้องเรียงใหม่→เก่า ห้ามซ้ำ

ตัวตรวจนี้จับของจริงได้ตั้งแต่รันครั้งแรก: มันบอกว่า `package.json` ยังเป็น `2.3.4` ขณะที่ matrix
ประกาศ `3.0.0` แล้ว

## Deprecation

| กติกา | ค่า |
|---|---|
| ต้องประกาศก่อนถอดออก | ใน MINOR release อย่างน้อยหนึ่งรุ่น |
| ระยะเวลาแจ้งขั้นต่ำ | **90 วัน** นับจาก `announcedAt` |
| ต้องมีอะไรมาแทน | `replacement` เป็นฟิลด์บังคับ |
| ทางย้าย | `migration` — ถ้าเป็น manual ต้องบอกว่าทำอย่างไร |

การประกาศและถอดออกในรีลีสเดียวกันทำได้เฉพาะเมื่อมี `note` อธิบายเหตุผล และ
`check-compatibility.js` จะปฏิเสธถ้าไม่มี — เพื่อให้แยกออกว่าอะไรคือข้อยกเว้นที่คิดมาแล้ว
กับอะไรคือความพลั้งเผลอ

### ข้อยกเว้นเดียวที่มีอยู่ตอนนี้ และทำไมถึงบันทึกไว้แบบนั้น

`pack` v1 ถูกประกาศเลิกใช้และถอดออกใน `3.0.0` รุ่นเดียวกัน โดย**ไม่มีระยะแจ้งล่วงหน้าเลย**
บันทึกตามจริงแทนที่จะย้อนวันให้ดูเรียบร้อย เพราะตอนที่เปลี่ยน kit ยังไม่มีนโยบายนี้ — ซึ่งคือช่องว่าง
ที่ EV-007 ปิดพอดี ภายใต้นโยบายที่ใช้อยู่ตอนนี้ การเปลี่ยนแบบนั้นต้องมี MINOR release ประกาศก่อน
และนี่คือครั้งสุดท้ายที่ได้รับอนุญาตให้ข้าม

## ความสัมพันธ์กับไฟล์ที่มีอยู่แล้ว

| ไฟล์ | หน้าที่ |
|---|---|
| `schemas/compatibility.json` | **ความจริงที่เครื่องอ่าน** — รุ่นไหนอ่านอะไรได้ อะไรถูก deprecate |
| `VERSION.md` | changelog สำหรับคน — เกิดอะไรขึ้นและทำไม |
| `UPGRADE.md` | ขั้นตอนลงมือ ต่อคู่เวอร์ชัน |
| เอกสารนี้ | กติกาที่ทั้งสามไฟล์ข้างบนต้องเคารพ |

ทุก MAJOR ต้องมีหัวข้อใน `UPGRADE.md` เสมอ — MAJOR ที่ไม่มีทางอัปเกรดเขียนไว้ คือ MAJOR
ที่ผลักภาระให้ผู้ใช้ไปเดาเอง

## v3.0.0 — รีลีสแรกที่อยู่ภายใต้นโยบายนี้

เป็น MAJOR เพราะ `pack` ขึ้นจาก 1.0 เป็น 2.0 และ migration เป็น `manual`:
v1 ไม่เคยบันทึกคำสั่ง setup ไว้ที่ไหนเลย จึงไม่มีอะไรให้แปลงเป็น recipe ได้โดยอัตโนมัติ
โปรเจกต์ที่มี `.claude/packs/*.json` ต้องเขียนใหม่ด้วยมือ — **ผู้ใช้ต้องลงมือ จึงเป็น MAJOR**
ตามเกณฑ์ข้อเดียวข้างบน ไม่ว่าจะมีคนมองว่ามันเป็นแค่การเปลี่ยนชื่อฟิลด์หรือไม่
