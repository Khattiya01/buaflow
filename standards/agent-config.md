# มาตรฐานการเขียน config ให้ AI

> เอกสารนี้ตอบคำถามว่า **"กฎข้อนี้ควรไปอยู่ที่ไหน"**
> เขียนผิดที่ = กฎเงียบหายไปโดยไม่มี error บอก หรือกิน context ทิ้งทุก session

---

## 1. สี่ชั้น และวิธีเลือก

| ชั้น | ที่อยู่ | โหลดเมื่อ | กิน context | ความแข็ง |
|---|---|---|---|---|
| **ความรู้ที่ต้องรู้ตลอด** | `AGENTS.md` (+ `CLAUDE.md` ที่ import) | ทุก session | ทุก request | แนะนำ |
| **ข้อบังคับเฉพาะโซนไฟล์** | `.claude/rules/*.md` + `paths:` | เมื่อแตะไฟล์ที่ match | เฉพาะตอนเกี่ยว | แนะนำ ตรงจุด |
| **ขั้นตอน / ความรู้ที่ใช้บางครั้ง** | `.claude/skills/<ชื่อ>/SKILL.md` | เมื่อถูกเรียกหรือ Claude เห็นว่าเกี่ยว | description ทุก session, เนื้อเต็มตอนใช้ | แนะนำ |
| **กฎที่ห้ามพัง** | `.claude/hooks/` + `settings.json` | ทุกครั้งที่ event ตรง | 0 | **บังคับจริง** |

**ผังตัดสิน:**

```
กฎนี้ถ้าพังแล้วเจ็บจริงไหม
├─ ใช่ → hook (และเขียน eval กันถอยหลัง)
└─ ไม่
   ├─ ผูกกับไฟล์กลุ่มหนึ่งไหม        → rule + paths:
   ├─ เป็นขั้นตอนยาวเกิน ~30 บรรทัดไหม → skill
   └─ เป็นข้อเท็จจริงที่ต้องรู้ทุกครั้ง  → AGENTS.md
```

**กฎการเลื่อนชั้น:** เขียนไว้แล้วแต่ AI ยังพลาดซ้ำ = คำแนะนำไม่พอ → เลื่อนขึ้นชั้นที่แข็งกว่า

## 2. `AGENTS.md` — เขียนยังไงให้ได้ผล

- **ยาวไม่เกิน ~200 บรรทัด** เกินกว่านี้ AI จะเริ่มมองข้ามกฎบางข้อ
  อาการ: "บอกไปแล้วทำไมไม่ทำ" → สงสัยความยาวก่อนสงสัยโมเดล
- เกณฑ์ตัดทุกบรรทัด: **"ถ้าลบบรรทัดนี้ AI จะทำผิดไหม"** ถ้าไม่ผิด → ตัด
- เขียนให้ **เจาะจงจนตรวจได้**: "ใช้ 2-space indent" ไม่ใช่ "format ให้สวย"
- ต้องไม่มีกฎที่ขัดกันเอง — ถ้าขัด AI จะเลือกเองแบบสุ่ม
- ถ้ามีข้อเดียวที่โดนข้ามบ่อย ให้เน้นเฉพาะข้อนั้น — **ถ้าเน้นทุกข้อ = ไม่ได้เน้นอะไรเลย**

| ✅ ควรมี | ❌ ไม่ควรมี |
|---|---|
| คำสั่งที่ AI เดาเองไม่ได้ | อะไรที่อ่านโค้ดแล้วรู้เอง |
| convention ที่ต่างจากค่า default ของภาษา | convention มาตรฐานที่โมเดลรู้อยู่แล้ว |
| กติกา branch / commit | API docs แบบละเอียด (ให้ลิงก์ไป) |
| ข้อควรระวังที่ไม่ชัดเจนในตัวโค้ด | คำอธิบายไฟล์ทีละไฟล์ |
| **ตัวอย่าง output ตอนที่ทุกอย่างผ่าน** | คำแนะนำลอย ๆ เช่น "เขียนโค้ดให้สะอาด" |

**ทำไมต้องมี `AGENTS.md` แยกจาก `CLAUDE.md`:** `AGENTS.md` เป็นมาตรฐานกลางที่เครื่องมืออื่น
(Codex, Cursor, Copilot, Gemini CLI, Windsurf) อ่านได้ด้วย ส่วน `CLAUDE.md` แค่ `@AGENTS.md`
แล้วต่อด้วยของเฉพาะ Claude Code — วันที่เปลี่ยนเครื่องมือ ความรู้โปรเจกต์ไม่หายไปด้วย

## 3. `.claude/rules/` — กฎที่ผูกกับไฟล์

```markdown
---
paths:
  - "src/api/**/*.ts"
  - "src/modules/**/*.ts"
---

# กติกา API
- ทุก endpoint ต้อง validate input ด้วย zod
```

- **rule ที่ไม่มี `paths:` จะโหลดทุก session** เหมือน `AGENTS.md` → ใส่ `paths:` เสมอ เว้นแต่ตั้งใจ
- 1 ไฟล์ 1 โดเมน ตั้งชื่อให้รู้เรื่อง (`backend-api.md` ไม่ใช่ `rules2.md`)
- **ใส่เหตุผลไม่ใช่แค่กฎ** — AI ที่รู้ว่าทำไม จะตัดสินใจถูกในกรณีที่กฎไม่ครอบคลุม
- **อันตรายที่ต้องระวัง:** โครงโฟลเดอร์เปลี่ยนแล้ว `paths:` ไม่ match อีก → rule เงียบไปเลย
  โดยไม่มี error บอก ต้องตรวจในรอบ Phase 8 ทุกครั้ง

## 4. `.claude/skills/` — ขั้นตอนที่ทำซ้ำ

```markdown
---
name: deploy
description: ปล่อยของขึ้น staging ใช้เมื่อ task ในรอบเสร็จหมดและผ่าน verify แล้ว
disable-model-invocation: true
allowed-tools: Bash(git *) Bash(pnpm *)
argument-hint: "<env>"
---
```

**frontmatter ที่ใช้บ่อย:**

| field | ใช้ทำอะไร |
|---|---|
| `description` | **ตัวตัดสินว่า Claude จะหยิบมาใช้เองไหม** ต้องบอกเงื่อนไขที่ควรใช้ ไม่ใช่แค่ชื่อความสามารถ |
| `disable-model-invocation: true` | คนเรียกได้อย่างเดียว — ใช้กับ skill ที่มี side effect (deploy, merge, ปิดงาน) |
| `user-invocable: false` | Claude อ่านได้อย่างเดียว — ใช้กับ skill ที่เป็นความรู้ล้วน |
| `allowed-tools` | pre-approve เครื่องมือเฉพาะเทิร์นนั้น ลด prompt โดยไม่เปิดสิทธิ์ถาวร |
| `context: fork` + `agent:` | ให้ skill รันใน subagent แยก context |
| `paths` | ให้ skill โผล่เฉพาะตอนทำงานกับไฟล์บางกลุ่ม |

**เทคนิค dynamic context** — ยิงคำสั่งแล้วฝังผลลัพธ์เข้า skill ก่อน Claude อ่าน:

````markdown
## สถานะปัจจุบัน
!`git status --short`
````

ใช้กับ `/review` เพื่อให้ได้ diff มาในมือทันทีโดยไม่ต้องเสียเทิร์นสั่งให้ไปรัน
**ข้อควรระวัง:** ถ้าคำสั่ง exit non-zero การเรียก skill จะถูกยกเลิกทั้งอัน — ใช้คำสั่งที่ไม่ค่อยพัง

**กติกาการเขียน:**
- ไม่เกิน ~150 บรรทัด รายละเอียดแยกไปไฟล์ประกอบในโฟลเดอร์เดียวกัน แล้วลิงก์ถึง
- เขียนเป็นขั้นตอนสั่งการ ไม่ใช่เรียงความ (ทุกบรรทัดคือ token ที่จ่ายซ้ำทุกครั้งที่ใช้)
- **description ห้ามทับกัน** ระหว่าง skill ไม่งั้น Claude หยิบผิดตัว

> `.claude/commands/*.md` แบบเดิมยังใช้ได้ แต่ **skills คือรูปแบบที่ควรใช้กับของใหม่**
> เพราะแนบไฟล์ประกอบได้ คุมได้ว่าใครเรียกได้ และ Claude โหลดเองได้เมื่อเกี่ยว

## 5. Hooks — ชั้นที่บังคับได้

| exit | ผล |
|---|---|
| `0` | ผ่าน (พิมพ์ JSON ออก stdout ได้เพื่อส่ง context เพิ่ม) |
| `2` | **บล็อก** — stderr ถูกส่งให้ Claude อ่านเป็นเหตุผล |
| อื่น | hook พังเอง งานเดินต่อ |

**event ที่ใช้บ่อย:** `PreToolUse` (บล็อกก่อนทำ), `PostToolUse` (format/lint หลังแก้),
`SessionStart` (ฉีด context ตั้งต้น), `Stop` (ไม่ให้จบเทิร์นจนกว่าเงื่อนไขจะผ่าน)

**หลักการเขียน:**
- ข้อความที่ส่งกลับต้องบอก **ทางที่ถูก** ไม่ใช่แค่บอกว่าห้าม — ไม่งั้น AI จะหาทางอ้อม
- เขียนให้ไม่มี dependency (Node ล้วน) เพื่อให้รันได้ทุกเครื่องและใน container
- hook พังต้องไม่ทำให้ทำงานไม่ได้ → จับ error แล้ว exit 0
- **hook ที่บล็อกงานปกติบ่อย ๆ ถือเป็นบั๊ก** ให้แก้เงื่อนไขให้แคบลง
  (hook ที่ขวางบ่อยจะทำให้คนปิดทั้งชุด ซึ่งแย่กว่าไม่มี)

## 6. Subagents

ใช้เมื่อ **อ่านของเยอะแต่คายกลับนิดเดียว** เท่านั้น — ไม่ใช่เพื่อจำลองตำแหน่งงาน

| ใช้ | ไม่ใช้ |
|---|---|
| รีวิว diff ด้วย context ที่สะอาด | แบ่งบทบาท PM / QA / DevOps |
| สำรวจโค้ดเก่าขนาดใหญ่ | งานที่ต้องเห็นบทสนทนาก่อนหน้า |
| งานที่ output ยาวและไม่ต้องอ่านซ้ำ | งานที่อยากดูและแก้ทิศทีละขั้น |

**คำเตือนสำคัญ:** reviewer subagent ที่ถูกสั่งให้ "หาปัญหา" จะหาเจอเสมอ แม้งานจะดีอยู่แล้ว
ต้องสั่งให้ **รายงานเฉพาะสิ่งที่กระทบความถูกต้องหรือ requirement** ไม่งั้นจะได้ over-engineering

## 7. Evals — regression test ของ config

config คือโค้ดชนิดหนึ่ง แต่ไม่มีอะไรบอกว่ามันพัง
เขียน eval จาก **ความพลาดจริง** (ไม่ใช่เคสที่คิดขึ้นเอง) แล้วรันใน session ใหม่ที่สะอาด
ก่อน merge การแก้ config ครั้งใหญ่ และเมื่อเปลี่ยนโมเดล

**เทคนิคตรวจว่า rule/skill ทำงานจริง:** รันเคสเดียวกันทั้งเปิดและปิดตัวนั้น
ถ้าผลเหมือนกัน แปลว่ามันไม่ได้ทำอะไรเลย → เขียนใหม่หรือลบทิ้ง

## 8. อาการผิดปกติที่พบบ่อย

| อาการ | สาเหตุที่แท้จริง | แก้ |
|---|---|---|
| บอกกฎไปแล้วแต่ยังทำผิด | `AGENTS.md` ยาวเกิน กฎถูกกลบ | ตัดให้สั้น หรือเลื่อนชั้นเป็น rule/hook |
| rule ไม่ทำงานเลย | `paths:` ไม่ match โครงจริง | ตรวจด้วย `/context` และ hook `InstructionsLoaded` |
| Claude เรียก skill ผิดตัว | `description` ทับกัน | เขียน description ให้ระบุเงื่อนไขที่ชัดและไม่ซ้อนกัน |
| แก้ซ้ำหลายรอบไม่ผ่านสักที | context เต็มไปด้วยทางที่ล้มเหลว | `/clear` แล้วเริ่มใหม่ด้วยโจทย์ที่ชัดกว่า — **ห้ามไล่แก้เกิน 2 รอบ** |
| งานบานปลายทุกครั้ง | ไม่มี plan ที่ commit ไว้ให้เทียบ | บังคับ `/plan` ก่อนงานที่แตะหลายไฟล์ |
