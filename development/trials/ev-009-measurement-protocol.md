# วิธีวัด reviewer-minutes และ TPC — protocol สำหรับ trial ของ EV-009

> **เขียนให้คนที่จะไปวัดจริง** ไม่ใช่ให้ AI อ่าน
> ใช้ได้กับ trial ตัวถัดไปด้วย ไม่ใช่เฉพาะ Bluepeak Hub

EV-009 ต้องการตัวเลข 4 ตัว · วันนี้ได้มาแล้ว 2:

| ตัวเลข | สถานะ | ค่า |
|---|---|---|
| Time to First Runnable (TFR) | ✅ วัดแล้ว | **113 วินาที** จากเครื่องเปล่า |
| คำถามที่มนุษย์ต้องตอบ | ✅ วัดแล้ว | **0** เพื่อให้รันได้ · **3** เพื่อปิด Phase A |
| **reviewer-minutes** | ❌ ยังไม่ได้วัด | ต้องมีคนรีวิวงาน AI จริง |
| **Time to Production Candidate (TPC)** | ❌ ยังไม่ได้วัด | ต้องไปถึง R3 จริง |

## กฎข้อเดียวที่ทำให้การวัดนี้รอด

> **ถ้าการวัดกินเวลาเกิน 1 นาทีต่องาน มันจะถูกเลิกทำภายในสองสัปดาห์**

ทุกอย่างข้างล่างออกแบบมาให้จดเสร็จใน ~20 วินาที และ**ไม่ต้องมีเครื่องมือใหม่** —
ใช้ไฟล์ task ที่เขียนอยู่แล้ว

## 1. reviewer-minutes

### นิยามที่ต้องตกลงก่อน ไม่งั้นตัวเลขเทียบกันไม่ได้

**reviewer-minutes = เวลาที่ _คน_ ใช้ตรวจงานที่ AI บอกว่าเสร็จแล้ว**

| นับ | ไม่นับ |
|---|---|
| อ่าน diff | เวลารอ AI ทำงาน |
| รันของจริงดูเอง | เวลารอ CI / gate |
| เขียน comment ตีกลับ | เวลาที่ AI แก้ตามที่ตีกลับ |
| อ่านซ้ำรอบที่สอง | เวลาพัก / สลับไปทำอย่างอื่น |

⇒ มันคือ **ต้นทุนของคน** ไม่ใช่เวลาที่ผ่านไปบนนาฬิกา

### วิธีจด

เพิ่ม 2 บรรทัดใน frontmatter ของไฟล์ task ตอนปิดงาน (ทดสอบแล้วว่า `docs-lint`
และ `board.js` ไม่แตะฟิลด์ที่ไม่รู้จัก):

```yaml
reviewRounds: 2       # ตีกลับกี่รอบกว่าจะผ่าน · ผ่านรอบแรก = 1
reviewMinutes: 18     # นาทีที่คนใช้ตรวจ รวมทุกรอบ
```

**วิธีจับเวลาที่ไม่ทรมาน:** เปิด diff = เริ่มจับ · approve หรือกดตีกลับ = หยุด ·
ปัดเป็นนาทีเต็ม ไม่ต้องละเอียดกว่านั้น จะใช้นาฬิกาจับเวลาในมือถือก็ได้

> ลืมจด = ใส่ `reviewMinutes: unknown` **อย่าเดาย้อนหลัง** ตัวเลขที่เดาขึ้นมาแย่กว่าไม่มีตัวเลข

### อ่านผลยังไง

```bash
node -e "
const fs=require('fs');const d='docs/backlog/tasks';
const rows=fs.readdirSync(d).filter(f=>f.endsWith('.md')).map(f=>{
  const t=fs.readFileSync(d+'/'+f,'utf8');
  const g=k=>(t.match(new RegExp('^'+k+':\\\\s*(.+)\$','m'))||[])[1];
  return {id:g('id'),m:Number(g('reviewMinutes')),r:Number(g('reviewRounds'))};
}).filter(x=>Number.isFinite(x.m));
if(!rows.length) return console.log('ยังไม่มีข้อมูล');
const med=a=>{const s=[...a].sort((x,y)=>x-y);return s[Math.floor(s.length/2)]};
console.log('งานที่วัดแล้ว:',rows.length);
console.log('reviewer-minutes มัธยฐาน:',med(rows.map(x=>x.m)));
console.log('รวมทั้งหมด:',rows.reduce((s,x)=>s+x.m,0),'นาที');
console.log('ผ่านรอบแรก:',Math.round(rows.filter(x=>x.r===1).length/rows.length*100)+'%');
"
```

### ตัวเลขไหนแปลว่าอะไร

**ตัวที่สำคัญกว่าคือ \"ผ่านรอบแรกกี่ %\" ไม่ใช่จำนวนนาที**

| สัญญาณ | แปลว่า |
|---|---|
| ผ่านรอบแรก **< 50%** | AI ไม่เข้าใจ convention ของโปรเจกต์ → ปัญหาอยู่ที่ `AGENTS.md` / rules ไม่ใช่ที่ AI |
| reviewer-minutes **สูงแต่ผ่านรอบแรก** | งานถูกแต่ diff ใหญ่เกินไป → task ซอยเล็กลง |
| reviewer-minutes **ต่ำและผ่านรอบแรกสูง** | นี่คือสิ่งที่ kit สัญญาไว้ว่าจะให้ |
| reviewer-minutes **ต่ำแต่ตีกลับบ่อย** | ⚠️ อันตราย — แปลว่ารีวิวแบบผ่าน ๆ ไม่ใช่ AI เก่งขึ้น |

**เก็บกี่งานถึงพอ:** ~10 งานได้สัญญาณ · ~30 งานเชื่อถือได้
⛔ อย่าเทียบข้าม type (`feat` กับ `docs` ใช้เวลารีวิวคนละโลก) — ดูแยกเมื่อมีข้อมูลพอ

## 2. TPC — Time to Production Candidate

### ⚠️ ความจริงที่ต้องรู้ก่อน: ตอนนี้ยังวัดเต็มไม่ได้

TPC = เวลาจากรับโปรเจกต์เข้าระบบ **จนกว่า `readiness --level R3` จะผ่าน**

Bluepeak Hub วันนี้อยู่ที่ **R1 ผ่านเต็ม · R2 ติด `ci` ข้อเดียว** และ R3 ยังต้องการอีกหลายอย่าง
(SBOM · secrets scan · perf/a11y budget · clean-environment rehearsal · backup/restore rehearsal ·
security baseline · supply-chain · operational-readiness)

**ถ้ารอให้ถึง R3 ก่อนแล้วค่อยได้ตัวเลข = ไม่ได้ตัวเลขไปอีกนาน** ⇒ วัดเป็นช่วงแทน

### วิธีที่ใช้ได้จริง: จับเวลาเป็นช่วง ไม่ใช่ก้อนเดียว

| ช่วง | เริ่มนับ | หยุดนับ | Bluepeak Hub |
|---|---|---|---|
| **adopt → R1** | commit แรกที่รับ kit | `readiness --level R1` ผ่าน | ✅ **เสร็จแล้ว** — ทั้งคู่อยู่ใน session เดียว |
| **R1 → R2** | R1 ผ่าน | `readiness --level R2` ผ่าน | 🚧 ติด billing ของ GitHub |
| **R2 → R3** | R2 ผ่าน | `readiness --level R3` ผ่าน | ⬜ ยังไม่เริ่ม |

**TPC = ผลรวมของสามช่วง** และได้ประโยชน์ทันทีตั้งแต่ช่วงแรก ไม่ต้องรอจนจบ

### จดที่ไหน

`docs/planning/_state.md` มีอยู่แล้ว เพิ่มตารางเดียว:

```markdown
## นาฬิกา TPC

| ช่วง | เริ่ม | จบ | ชั่วโมงคน | หมายเหตุ |
|---|---|---|---|---|
| adopt → R1 | 2026-09-23 | 2026-09-23 | ~2 | session เดียว |
| R1 → R2 | 2026-09-23 | — | — | ติด GitHub billing ตั้งแต่ 2026-09-23 |
| R2 → R3 | — | — | — | |
```

> **จด \"ชั่วโมงคน\" ไม่ใช่ \"ผ่านไปกี่วัน\"** — ถ้าจดวัน ตัวเลขจะโดนวันหยุดกับการรอคนอื่น
> กลืนจนไม่เหลือความหมาย · ช่วงที่ติดรออะไรอยู่ ให้เขียนไว้ในหมายเหตุแยก

### จุดที่ต้องระวังที่สุด

⛔ **อย่านับเวลาที่ติดรอของที่ไม่เกี่ยวกับ kit รวมเข้าไปใน TPC**

ตอนนี้ R1→R2 ติดที่ **billing ของ GitHub** ซึ่งไม่ได้แปลว่า Buaflow ช้า
ถ้าเอาเวลานั้นมารวม ตัวเลขจะโทษเครื่องมือผิดตัว

⇒ แยกเป็นสองคอลัมน์ไปเลย: **\"ชั่วโมงคนที่ลงแรงจริง\"** กับ **\"ติดรออะไรอยู่\"**

---

## 3. ลำดับที่แนะนำให้ทำ

1. **เริ่มจด `reviewRounds` / `reviewMinutes` ตั้งแต่ task ถัดไป** — ถูกที่สุด ได้สัญญาณเร็วที่สุด
   และไม่ต้องรอปลดล็อกอะไรเลย
2. **แก้ GitHub billing** → CI รันได้ → `ci` เป็น pass → **R2** → ได้ตัวเลขช่วง R1→R2 จริง
3. ค่อยตัดสินใจเรื่อง R3 หลังเห็นตัวเลขสองตัวแรกแล้ว — **อย่าไล่ทำ R3 เพราะอยากได้ตัวเลข**
   ถ้ายังไม่มีเหตุผลทางธุรกิจรองรับ

## 4. สิ่งที่จะทำให้ตัวเลขชุดนี้ไร้ค่า

| กับดัก | ทำไมถึงพัง |
|---|---|
| ให้ AI ตัวที่ทำงานเป็นคนจดเวลารีวิว | คนทำกับคนตรวจเป็นคนเดียวกัน = ตัวเลขที่ไม่มีความหมาย (ปัญหาเดียวกับที่ EV-009 มีอยู่เพื่อแก้) |
| เดาย้อนหลังตอนสิ้นเดือน | ความจำคนเข้าข้างตัวเองเสมอ ⇒ `unknown` ดีกว่า |
| วัดเฉพาะงานที่ราบรื่น | งานที่ตีกลับ 4 รอบคือข้อมูลที่มีค่าที่สุด ห้ามข้าม |
| เอา TPC ไปเทียบกับโปรเจกต์อื่นที่คนละขนาด | TPC ไม่ normalize ตามขนาด — เทียบได้เฉพาะกับตัวเองข้ามเวลา |
