# EV-011 เก็บข้อมูลการใช้งานภายใน (opt-in) — Requirements

- ที่มา: `development/state.json` งาน EV-011 และ decision D-028 (repo นี้ไม่ใช้ `docs/intents/` — งานพัฒนาตัว Buaflow ติดตามใน state.json)
- สถานะ: อนุมัติแล้ว (2026-09-24)

## ปัญหาและเป้าหมาย

- **ปัญหาที่แก้:** Buaflow ถูกใช้จริงในโปรเจกต์ภายใน 2–5 โปรเจกต์ผ่าน plugin แต่ผลจากงานจริงไม่กลับมาช่วยพัฒนา Buaflow เลย ทุกอย่างที่รู้ตอนนี้มาจาก reference app ที่ Buaflow เขียนเอง กับ trial ครั้งเดียว (EV-009) ที่ต้องวัดด้วยมือตาม `ev-009-measurement-protocol.md`
- **ใครได้ประโยชน์:** เจ้าของ Buaflow (คนพัฒนา kit) และทีมที่ใช้ Buaflow ในโปรเจกต์ภายใน
- **วัดความสำเร็จยังไง:**
  1. มีโปรเจกต์ภายในอย่างน้อย 2 โปรเจกต์ (ไม่นับ repo นี้) เปิดเก็บและมีข้อมูลเข้าที่เก็บกลางแล้ว
  2. จากที่เก็บกลางอย่างเดียว โดยไม่ต้องเปิดโปรเจกต์ใด ๆ ทำได้ครบ 4 อย่าง: สร้างร่าง eval case จากงานจริง, เทียบผล `/check` แยกตาม model, ดู readiness และอายุหลักฐานของทุกโปรเจกต์ในหน้าเดียว, และเปิดดูงานจริงของ task ใดก็ได้เป็นเคสอ้างอิง
  3. การเก็บข้อมูลไม่ทำให้ task, commit หรือ gate ช้าลงหรือล้มแม้แต่ครั้งเดียว

## User Story

- ในฐานะ**เจ้าของ Buaflow** ฉันต้องการเห็นว่าทุกโปรเจกต์ภายในใช้ Buaflow แล้วเกิดอะไรขึ้นจริง เพื่อปรับ skill จากหลักฐาน ไม่ใช่จากความรู้สึก
- ในฐานะ**เจ้าของ Buaflow** ฉันต้องการเอา intent, plan และ AC จากงานจริงมาเป็น eval case เพื่อรู้ว่าการแก้ skill ทำให้ดีขึ้นหรือแย่ลง
- ในฐานะ**เจ้าของ Buaflow** ฉันต้องการเทียบว่า model แต่ละตัวทำให้ `/check` ตกบ่อยแค่ไหนและต้องแก้งานกี่รอบ เพื่อเลือก model ให้เหมาะกับแต่ละขั้น
- ในฐานะ**คนในทีมที่ใช้ Buaflow** ฉันต้องการตอบครั้งเดียวว่ายอมให้เก็บไหม แล้วไม่ต้องถูกถามหรือถูกรบกวนอีก

## Acceptance Criteria — เขียนแบบ EARS

### ความยินยอม

- [ ] **AC-1** WHEN `/buaflow:start` ทำงานในโปรเจกต์ที่ยังไม่มีคำตอบยินยอม THE SYSTEM SHALL ถามผู้ใช้ 1 ครั้งว่าจะเปิดเก็บข้อมูลการใช้งานไหม และบันทึกคำตอบ (เปิด/ปิด พร้อมวันที่และผู้ตอบ) ลงไฟล์ในโปรเจกต์
  - ตัดสินตอนทำ EV-011.7 (2026-09-24, เจ้าของ): ถามเฉพาะบนเครื่องที่ตั้งค่าที่เก็บกลางแล้ว (`~/.buaflow/usage.json` มีอยู่) เพราะ plugin เป็น public แต่ feature นี้ใช้ภายในเท่านั้นตาม R1 — คนนอกจึงไม่เห็นคำถาม ส่วนคนภายในต้องรัน `buaflow usage setup` ก่อน `/buaflow:start`
- [ ] **AC-2** WHILE โปรเจกต์ยังไม่มีคำตอบยินยอม หรือคำตอบเป็น "ปิด" THE SYSTEM SHALL ไม่สร้างไฟล์ event, ไม่เขียนข้อมูลใด ๆ ลงที่เก็บ และไม่ sync
- [ ] **AC-3** WHEN โปรเจกต์มีคำตอบยินยอมอยู่แล้ว THE SYSTEM SHALL ไม่ถามซ้ำ ทั้งตอน `/buaflow:start` แบบ resume และแบบ upgrade
- [ ] **AC-4** WHEN ผู้ใช้เปลี่ยนคำตอบในไฟล์ยินยอมเป็น "ปิด" THE SYSTEM SHALL หยุดบันทึกตั้งแต่ event ถัดไป โดยไม่ลบข้อมูลที่เก็บไปแล้ว
- [ ] **AC-5** WHILE โปรเจกต์เปิดเก็บอยู่ THE SYSTEM SHALL แสดงข้อความ 1 บรรทัดตอนเปิด session ว่ากำลังเก็บข้อมูล และบอกวิธีปิด

### การบันทึก event

- [ ] **AC-6** WHEN มีการสร้างไฟล์ intent ใหม่ใน `docs/intents/` THE SYSTEM SHALL บันทึก event `intent.opened` พร้อมเนื้อหาไฟล์
- [ ] **AC-7** WHEN ไฟล์ plan ใน `docs/plans/` ถูกอนุมัติ THE SYSTEM SHALL บันทึก event `plan.approved` พร้อมเนื้อหา plan
- [ ] **AC-8** WHEN task ถูกสร้างใน `docs/backlog/tasks/` THE SYSTEM SHALL บันทึก event `task.created` พร้อม AC, estimate และลิงก์ `fixes:` ถ้ามี
- [ ] **AC-9** WHEN `status` ของ task เปลี่ยน THE SYSTEM SHALL บันทึก event `task.status` พร้อมสถานะเดิมและสถานะใหม่ ทั้งเปลี่ยนไปข้างหน้าและย้อนกลับ
- [ ] **AC-10** WHEN `/check` สรุปผลเสร็จ THE SYSTEM SHALL บันทึก event `check.result` พร้อมผลตัดสิน (ผ่าน/ไม่ผ่าน) และรายการข้อที่เจอตามที่รายงาน
- [ ] **AC-11** WHEN `buaflow audit` ทำงานเสร็จ THE SYSTEM SHALL บันทึก event `verifier.audit` พร้อมจำนวน confirmed / refuted / unverifiable และรายการ control
- [ ] **AC-12** WHEN `/done` ปิด task หลัง merge THE SYSTEM SHALL บันทึก event `task.done` พร้อม commit hash, วันที่เริ่ม, วันที่ปิด และจำนวน session ที่ใช้ถ้านับได้
- [ ] **AC-13** THE SYSTEM SHALL ใส่ข้อมูลเหล่านี้ในทุก event: เวอร์ชัน schema, เวลา, ชื่อโปรเจกต์, task id (ถ้ามี), model ที่ทำงาน, เวอร์ชัน kit และ commit ปัจจุบันของโปรเจกต์
- [ ] **AC-14** IF ระบบไม่รู้ว่า session นั้นใช้ model อะไร THEN THE SYSTEM SHALL บันทึก model เป็น `unknown`
- [ ] **AC-15** THE SYSTEM SHALL ให้ task template มีช่อง `fixes: <task id>` สำหรับ task ที่แก้งานที่ปิดไปแล้ว

### Sync ไปที่เก็บกลาง

- [ ] **AC-16** WHEN เปิด session, จบ session หรือผู้ใช้สั่ง `buaflow usage sync` THE SYSTEM SHALL ส่ง event ที่ยังไม่ได้ sync ไปที่ private git repo ที่ตั้งค่าไว้
- [ ] **AC-17** IF sync ล้มเหลว (ไม่มีเน็ต, repo ใช้ไม่ได้, ไม่มีสิทธิ์) THEN THE SYSTEM SHALL เก็บ event ไว้ในเครื่อง, ไม่ทำให้ session หรือคำสั่งที่เรียกล้ม และลองใหม่ในรอบ sync ถัดไป
- [ ] **AC-18** IF เครื่องนั้นยังไม่ได้ตั้งค่าที่เก็บกลาง THEN THE SYSTEM SHALL เก็บ event ไว้ในเครื่อง และแจ้ง 1 บรรทัดตอนเปิด session ว่ายังไม่ได้ตั้งค่า พร้อมคำสั่งที่ใช้ตั้ง
- [ ] **AC-19** WHEN sync ซ้ำหลายรอบหรือจากหลายเครื่อง THE SYSTEM SHALL ไม่ทำให้ event ซ้ำหรือหายในที่เก็บกลาง
- [ ] **AC-20** THE SYSTEM SHALL ไม่ให้ event ของ Buaflow ถูก commit เข้า git ของโปรเจกต์ผู้ใช้ (มีแค่ไฟล์ยินยอมที่ commit)

### ใช้ประโยชน์จากที่เก็บกลาง

- [ ] **AC-21** WHEN สั่ง `buaflow usage eval-draft --task <โปรเจกต์>/<task id>` THE SYSTEM SHALL สร้างร่าง eval case ตาม `eval-case.schema.json` จาก intent, plan และ AC ของ task นั้น โดยระบุ `origin` กลับไปที่โปรเจกต์และ task ต้นทาง
- [ ] **AC-22** WHEN สั่ง `buaflow usage report` THE SYSTEM SHALL สร้างรายงานไฟล์เดียวจากที่เก็บกลาง ที่มีอัตรา `/check` ไม่ผ่าน, จำนวน task ที่สถานะย้อนกลับ และจำนวน task แก้ตามมา แยกตาม model
- [ ] **AC-23** WHEN สั่ง `buaflow usage report` THE SYSTEM SHALL แสดงในรายงานเดียวกันว่าแต่ละโปรเจกต์อยู่ readiness ระดับไหน และหลักฐานล่าสุดอายุกี่วัน
- [ ] **AC-24** WHEN สั่ง `buaflow usage show <โปรเจกต์>/<task id>` THE SYSTEM SHALL แสดง event ทั้งหมดของ task นั้นเรียงตามเวลา ตั้งแต่ intent จนถึง done
- [ ] **AC-25** IF event ในที่เก็บกลางมีเวอร์ชัน schema ที่เครื่องมือไม่รู้จัก THEN THE SYSTEM SHALL ข้าม event นั้น, นับจำนวนที่ข้ามแสดงในรายงาน และไม่ล้ม
- [ ] **AC-26** WHEN สั่ง `buaflow usage report` THE SYSTEM SHALL แสดงรายการ "task ที่ควรดู" คือ task ที่ `/check` ไม่ผ่าน, สถานะย้อนกลับ หรือมี task อื่นชี้มาด้วย `fixes:` เรียงจากสัญญาณมากไปน้อย พร้อมคำสั่ง `buaflow usage eval-draft` ของแต่ละ task ที่ copy ไปรันได้ทันที
- [ ] **AC-27** WHEN เปิด session ใน repo ของ Buaflow เองบนเครื่องที่ตั้งค่าที่เก็บกลางไว้ THE SYSTEM SHALL แจ้ง 1 บรรทัดว่ามี event ใหม่กี่รายการตั้งแต่ review ครั้งล่าสุด และ review ครั้งล่าสุดคือเมื่อไร (review = ครั้งล่าสุดที่สั่ง `buaflow usage report`)

### วงจรพัฒนา Buaflow จากข้อมูล (ทำโดยคน ไม่อัตโนมัติ)

การเก็บเป็นอัตโนมัติ แต่การแก้ skill ไม่อัตโนมัติโดยตั้งใจ: เจ้าของเปิด session ใน repo Buaflow → `report` → เลือก task จาก AC-26 → `eval-draft` → วงจร EV-006 เดิม (change-proposal → แก้ → eval ต้องผ่านและไม่ถดถอย → release) เพราะกติกาของ Buaflow ห้ามคนเขียน eval case เป็นคนตรวจ และห้าม merge เอง

## Non-functional

| เรื่อง | เกณฑ์ที่วัดได้ |
|---|---|
| ไม่ขวางงาน | การบันทึก 1 event ใช้เวลาไม่เกิน 200 ms · hook ตอนเปิด/จบ session คืนผลภายใน 1 วินาทีแม้ sync ยังไม่เสร็จ (sync ทำเบื้องหลัง) |
| ไม่ล้ม | ทุกกรณีล้มเหลวของการบันทึกและ sync ต้องคืน exit code 0 ให้ hook และไม่พิมพ์ error ที่ทำให้ Claude Code หยุดงาน |
| ปริมาณ | รองรับ 5 โปรเจกต์ × 1 ปี โดยทำ report ได้ภายใน 10 วินาที |
| dependency | ไม่เพิ่ม npm dependency — ใช้ Node กับ git ที่ kit ใช้อยู่แล้ว |
| ความปลอดภัย | ห้ามเก็บค่าจากไฟล์ `.env*` หรือ secret ที่ guard hook รู้จัก แม้จะเก็บเนื้อหาเต็ม (เนื้อหาเต็มหมายถึงเอกสาร intent/plan/task/ผล check ไม่ใช่ทุกไฟล์) |

## นอกขอบเขต (รอบนี้ไม่ทำ)

- ผู้ใช้ภายนอกองค์กร, การทำ anonymize และ privacy contract สำหรับคนนอก
- server หรือ dashboard แบบ real-time — รายงานเป็นไฟล์ที่สร้างเมื่อสั่ง
- เก็บ token และค่าใช้จ่ายของ model
- บันทึกทุก tool call หรือทุกข้อความในแชท — เก็บเฉพาะ event ตามขั้นตอนงานข้างบน
