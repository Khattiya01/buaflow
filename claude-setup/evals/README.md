# Evals — regression test ของ config

## ปัญหาที่แก้

`AGENTS.md`, rules, skills, hooks คือ **โค้ดชนิดหนึ่ง** — มันกำหนดพฤติกรรมของระบบ
แต่ต่างจากโค้ดตรงที่ไม่มีอะไรบอกว่ามันพัง

สิ่งที่ทำให้ config พังโดยไม่มีใครรู้:
- เพิ่มบรรทัดใน `AGENTS.md` จนยาวเกิน แล้วกฎเก่าเริ่มถูกมองข้าม
- แก้ rule แล้ว `paths:` ไม่ match อีกต่อไป — rule นั้นเงียบไปเลยโดยไม่มี error
- เปลี่ยนโมเดล แล้วพฤติกรรมบางอย่างเปลี่ยน
- เพิ่ม skill ใหม่ที่ description ทับกับของเดิม แล้ว Claude เรียกผิดตัว

eval คือชุดเคสที่รันซ้ำได้ เพื่อตอบว่า **"หลังเปลี่ยนแล้ว AI ยังทำเรื่องนี้ถูกอยู่ไหม"**

## รูปแบบ: เคสเป็น JSON ไม่ใช่ตารางที่คนกรอกเอง (EV-004)

รูปแบบเดิมเป็น Markdown ที่ลงท้ายด้วยตาราง "ผลการรันล่าสุด" ซึ่งคนกรอกเอง —
และ **ไม่มีอะไรบอกได้ว่าแถวนั้นตัดสินเคสเวอร์ชันไหน** พอแก้เคสให้ง่ายลง
แถวที่เขียนว่า "ผ่าน" ก็ยังอยู่ตรงนั้นและยังอ่านว่าผ่านอยู่ดี

ตอนนี้แยกเป็นสองอาร์ทิแฟกต์:

| ไฟล์ | คือ |
|---|---|
| `docs/evals/EV-0xx.json` | **เคส** — prompt + เกณฑ์ที่มี id คงที่ + เงื่อนไขผ่าน |
| `docs/evals/runs/*.json` | **ผลการรันหนึ่งครั้ง** — verdict รายข้อ + เวอร์ชันของเคสที่ตัดสิน |

สามกฎที่ Markdown ทำไม่ได้ และ `eval-harness.js` บังคับให้:

1. **run ตรึงเวอร์ชันของเคส** ผ่าน `caseRevision` — แก้ `prompt` หรือ `criteria` เมื่อไหร่
   run เก่ากลายเป็น **stale ทันที** ไม่ใช่กลายเป็นหลักฐานผ่านที่ตกค้าง
   (แก้ `title` หรือปลดเคสออก **ไม่** ทำให้ stale — สองอย่างนั้นไม่ได้เปลี่ยนสิ่งที่เคสถาม)
2. **คะแนนถูกคำนวณใหม่ทุกครั้ง** จาก verdict รายข้อ — run ที่สรุป `pass`
   ขณะที่ verdict ของตัวเองบอกตรงข้าม **ไม่ผ่าน**
3. **คนเขียนเคสไม่ใช่คนตรวจเคส** — `gradedBy` ต้องต่างจาก `authoredBy`
   และ `session: "continued"` ตกเสมอ เพราะเคสที่ผ่านด้วย context ที่ค้าง
   ไม่ได้พิสูจน์อะไรเกี่ยวกับ config

## วิธีสร้าง

ใช้ `docs/templates/eval-case.tpl.json` เก็บที่ `docs/evals/EV-0xx.json`

**ที่มาของเคสที่ดีที่สุดคือความพลาดจริง** ไม่ใช่เคสที่คิดขึ้นเอง —
เคสจึงต้องประกาศ `origin` และถ้าเป็น `observed-failure` ต้องมี `observedIn` ที่ตรวจกลับได้:

| เจออะไร | ทำ |
|---|---|
| AI ทำผิดเรื่องเดิมเป็นครั้งที่ 2 | เขียนลง `AGENTS.md` **และ** เขียน eval |
| มี incident บน prd ที่ต้นเหตุคือ AI ทำสิ่งที่ควรรู้ว่าห้ามทำ | เขียน eval — ห้ามพลาดซ้ำ |
| รีวิวเจอประเด็นเดิมซ้ำ ๆ | เขียน eval |

เริ่มที่ 10-20 เคสก็พอ ไม่ต้องครอบคลุมทุกอย่าง

ทุกเคสต้องมีเกณฑ์ทั้งฝั่ง **`must-happen`** และ **`must-not-happen`** อย่างน้อยอย่างละข้อ
เพราะความพลาดที่พบบ่อยกว่าของ AI คือ **การทำเกิน** ไม่ใช่การทำไม่ครบ

## วิธีรัน

**รันเมื่อไหร่:** ก่อน merge การแก้ `AGENTS.md` / rules / skills / hooks ครั้งใหญ่,
เมื่อเปลี่ยนโมเดล, และทุกครั้งที่ปิด milestone

```bash
node .claude/eval-harness.js --render docs/evals/EV-001.json     # อ่านเคสแบบคน
node .claude/eval-harness.js --revision docs/evals/EV-001.json   # hash ที่ต้องใส่ใน run
node .claude/eval-harness.js --cases docs/evals --runs docs/evals/runs
```

1. เปิด session ใหม่ **สะอาด** (`/clear`) — นี่คือข้อที่คนพลาดบ่อยที่สุด
   ถ้ารันต่อจาก session ที่เพิ่งคุยเรื่องนั้น มันจะผ่านเพราะ context ที่ค้าง ไม่ใช่เพราะ config ดี
   ⇒ บันทึกตามจริงเป็น `session: "continued"` แล้ว harness จะปฏิเสธให้เอง
2. วาง `prompt` (และ `followUpPrompt` ถ้ามี) จากไฟล์เคส
3. ตัดสินทีละเกณฑ์ตาม id — ตัดสินไม่ได้ให้ใส่ `unclear` **อย่าเดาว่า pass**
   (`unclear` นับเป็นไม่ผ่าน และถูกรายงานแยก เพราะมันคือข้อมูลว่า *เกณฑ์ข้อนั้น* เขียนไม่ชัด)
4. เขียน run record จาก `docs/templates/eval-run.tpl.json` ลง `docs/evals/runs/`

> ⛔ **อย่าให้ AI ตัวที่เพิ่งเขียน config เป็นคนตรวจ eval ของ config นั้น**
> ถ้ายังไม่มีคนอื่นมาตรวจ ปล่อยไว้เป็น baseline ที่ยังไม่ได้รันแล้วบอกตรง ๆ
> ดีกว่าได้ตัวเลขที่ไม่มีความหมาย

**เทคนิคสำคัญ — ทดสอบว่า rule/skill ทำงานจริงไหม:**

รันเคสเดียวกัน 2 รอบ คือ **เปิด** (`variant: "baseline"`) กับ **ปิด** (`variant: "ablation"`)
rule/skill นั้น ถ้าผลออกมาเหมือนกันทั้งสองรอบ แปลว่าไฟล์นั้นไม่ได้ทำอะไรเลย —
ให้เขียนใหม่ให้ชัดขึ้น หรือลบทิ้ง อย่าเก็บไว้ให้กิน context เปล่า ๆ

harness รายงานให้เองเมื่อมีข้อมูลครบ:

| รายงาน | แปลว่า |
|---|---|
| `unrun` | ไม่มี run ที่ตรงกับเวอร์ชันปัจจุบันของเคส — eval ที่ไม่มีใครรันคือเอกสารตาย |
| `ablation-unrun` | ไม่เคยรันรอบปิด ⇒ ยังไม่รู้ว่าไฟล์ที่เทสอยู่ทำอะไรจริงไหม |
| `ablation-inconclusive` | ปิดแล้วผลไม่เปลี่ยน ⇒ **ไฟล์นั้นไม่ใช่ตัวที่ทำให้เกิดพฤติกรรม** |
| `nondeterministic` | caseRevision + commit + model + variant เดียวกัน แต่ผลไม่ตรงกัน ⇒ ข้อมูลเกี่ยวกับ **เคส** ไม่ใช่โมเดล |
| `unclear-criteria` | มีเกณฑ์ที่คนตัดสินไม่ได้ ⇒ ต้องเขียนใหม่ |

## เคสตั้งต้น

ในโฟลเดอร์นี้มี 4 เคสที่ใช้ได้กับทุกโปรเจกต์ที่ใช้ kit นี้ —
คัดลอกไป `docs/evals/` ตอน Phase 7.11 (หรือ A.5 ถ้าเป็นโปรเจกต์เดิม)
แล้ว **แก้ `tests[]` ให้ชี้ไฟล์จริงของโปรเจกต์**

| ไฟล์ | เทสอะไร |
|---|---|
| `EV-001.json` | กฎ "ถามก่อนสร้าง component" ยังทำงานอยู่ไหม |
| `EV-002.json` | AI ยังทำเครื่องหมาย NEEDS CLARIFICATION แทนการเดาอยู่ไหม |
| `EV-003.json` | AI ยังแปะผลลัพธ์จริงก่อนบอกว่าเสร็จอยู่ไหม |
| `EV-004.json` | AI ยังไม่ merge เข้า main เอง และเปิด PR แทนอยู่ไหม (แม้ถูกกดดัน) |

⛔ `tests[]` ของเคสตั้งต้นชี้ไปที่ไฟล์ของ **kit** ไม่ใช่ของโปรเจกต์คุณ —
คัดลอกไปแล้วไม่แก้ harness จะฟ้องว่าไฟล์ไม่มีอยู่จริง ซึ่งเป็นความตั้งใจ

## รันอัตโนมัติ (ทางเลือก)

วิธีข้างบนคือรันมือใน session สะอาด — ใช้ได้ดีตอนเคสยังน้อย พอเกิน ~10 เคสจะไม่มีใครรันครบ
Claude Code มี `claude plugin eval` สำหรับรัน eval suite ของ skill แบบ non-interactive และให้รายงาน JSON
ใช้ skill `skill-creator` แปลงเคสในโฟลเดอร์นี้เป็น suite (มันมี flow วัด variance ให้ด้วย)
แล้วรันใน Phase 8.4 หรือใน CI job แยก (ห้ามใส่ใน gate ปกติ — มันเรียกโมเดล ช้าและมีค่าใช้จ่าย)

ตัวตรวจรูปแบบ (`eval-harness.js`) ไม่เรียกโมเดล จึงใส่ใน gate ปกติได้

## สิ่งที่ eval ไม่ใช่

- ไม่ใช่ที่ทดแทน unit test ของโค้ด
- ไม่ใช่ตัวชี้วัดคุณภาพโมเดล
- ไม่ใช่สิ่งที่ต้องทำให้ครบ 100% — eval ที่ไม่มีใครรันคือเอกสารตาย

**eval ต้องวิวัฒน์** เคสที่เคยแยกความต่างได้ พอโมเดลเก่งขึ้นก็จะผ่านหมดจนไร้ความหมาย
ถ้าเคสไหนผ่านติดกันหลายรอบและไม่เคยจับอะไรได้เลย ให้ใส่ `retired` แทนการลบ —
ประวัติว่ามันเคยจับอะไรได้ยังอยู่ และ harness จะเลิกรายงานว่ามันไม่ถูกรัน
