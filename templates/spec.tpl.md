# Spec Template (สำหรับ feature ใหญ่เท่านั้น)

เก็บที่ `docs/specs/<F-xx>-<ชื่อ>/` แยกเป็น 3 ไฟล์
**ต้องให้ผู้ใช้อนุมัติแต่ละไฟล์ก่อนไปไฟล์ถัดไป** และอนุมัติครบก่อนเขียนโค้ด

## กติกาที่ใช้กับทั้ง 3 ไฟล์

**1. ห้ามเดา — ใช้เครื่องหมายแทน**

ทุกจุดที่ไม่ชัดและมีผลต่อผลลัพธ์ ให้เขียนแบบนี้ **ห้ามเติมค่าที่ดูสมเหตุสมผลเอาเอง**:

```
[NEEDS CLARIFICATION: ผู้ใช้ที่ถูกระงับยังเห็นประวัติคำสั่งซื้อเดิมได้ไหม]
```

แล้วรวมทุก marker ไว้ท้ายไฟล์ในหัวข้อ "คำถามที่ยังไม่มีคำตอบ"
**ไฟล์ที่ยังเหลือ marker จะผ่าน gate ไปขั้นถัดไปไม่ได้** ต้องได้คำตอบแล้วลบ marker ออกก่อน

**2. ถามทีละกลุ่ม ไม่เกิน 4 ข้อ** และเสนอคำแนะนำพร้อมเหตุผลเสมอ ไม่ใช่ยิงคำถามเปล่า

**3. ถ้า design เปลี่ยนระหว่างทำ** ให้แก้ spec ก่อน แล้วค่อยแก้โค้ด
spec ที่ไม่ตรงกับโค้ดอันตรายกว่าไม่มี spec เพราะ AI จะเชื่อ spec

```markdown
## Acceptance Criteria — เขียนแบบ EARS

เขียนให้แปลงเป็นชื่อเทสได้ตรง ๆ ใช้ 4 แบบนี้เท่านั้น:

| แบบ | รูปประโยค | ใช้เมื่อ |
|---|---|---|
| Event | **WHEN** <เหตุการณ์> **THE SYSTEM SHALL** <ทำอะไร> | มีสิ่งกระตุ้นชัดเจน |
| State | **WHILE** <อยู่ในสถานะ> **THE SYSTEM SHALL** <ทำอะไร> | เงื่อนไขที่คงอยู่ช่วงหนึ่ง |
| Condition | **IF** <เงื่อนไข> **THEN THE SYSTEM SHALL** <ทำอะไร> | กรณีผิดปกติ / ข้อยกเว้น |
| Ubiquitous | **THE SYSTEM SHALL** <ทำอะไร> | กฎที่จริงตลอดเวลา |

- [ ] **AC-1** WHEN ผู้ใช้กดปุ่มบันทึกโดยกรอกครบ THE SYSTEM SHALL สร้าง record และตอบ 201 พร้อม id
- [ ] **AC-2** IF อีเมลซ้ำกับที่มีอยู่ THEN THE SYSTEM SHALL ตอบ 409 พร้อม code `EMAIL_TAKEN` และไม่สร้าง record
- [ ] **AC-3** WHILE คำขออยู่ระหว่างรออนุมัติ THE SYSTEM SHALL แสดงสถานะ pending และไม่ให้แก้ไขข้อมูล

> ห้ามเขียนคำว่า "จัดการ error ให้ดี" / "ใช้งานลื่นไหล" / "ปลอดภัย"
> เพราะเทสไม่ได้ ต้องระบุ **สิ่งกระตุ้น + ระบบ + พฤติกรรมที่ต้องเกิด**
```

# ไฟล์ 3 — `tasks.md` (แตกเป็นงาน)

```markdown
# <F-xx> <ชื่อ feature> — Tasks

| ID | งาน | ประเภท | ขึ้นกับ | ประมาณ | AC ที่ครอบ | ขนานได้ |
|---|---|---|---|---|---|---|
| T-0xx | Prisma model + migration | db | - | 0.5 | - | |
| T-0xx | POST /api/v1/... + unit test | api | T-0xx | 1 | AC-1, AC-2 | |
| T-0xx | หน้า ... (UI) | ui | T-0xx | 1 | AC-3 | [P] |
| T-0xx | อัปเดต OpenAPI + Postman | docs | T-0xx | 0.5 | - | [P] |
| T-0xx-test | unit test ของหน้า ... | test | ผ่าน review แล้ว | 0.5 | AC-3 | |

- `[P]` = ไม่ชนกับตัวอื่นในแถวเดียวกัน ทำสลับลำดับได้
  (แต่กติกาของโปรเจกต์ยังคือ **ทำทีละ 1 task** เครื่องหมายนี้ใช้บอกลำดับที่ยืดหยุ่นได้เท่านั้น)
- แต่ละ task ต้อง **จบได้ใน 1 session** ถ้าไม่จบ → แตกอีก
- backend task รวม unit test ในตัว
- frontend task ต้องมี task `-test` คู่เสมอ (สถานะ blocked)

## ลำดับที่แนะนำ
1. ...

## AC ที่ยังไม่มี task รองรับ
<ต้องว่าง ถ้าไม่ว่างแปลว่าแตก task ไม่ครบ>

| ความเสี่ยง | แผนรับมือ |
|---|---|

- [ ] ทุก AC มี task รองรับครบ
- [ ] ทุก task มี AC ที่ครอบ หรือระบุชัดว่าเป็นงาน infra ที่ไม่ผูก AC
- [ ] สร้างไฟล์ `docs/backlog/tasks/T-xxx.md` ครบทุกตัวแล้ว
- [ ] เพิ่มลง `docs/backlog/board.md` แล้ว
- [ ] ผู้ใช้อนุมัติแล้ว
```

## กติกาการใช้ spec

- **feature ใหญ่ = ต้องมี spec ก่อนเขียนโค้ด** (ไม่มีข้อยกเว้น)
- task ย่อยใน feature ที่มี spec แล้ว = ไม่ต้องทำ spec ใหม่ ใช้ไฟล์ task + อ้าง spec แม่
- bug / hotfix = ไม่ต้องมี spec ใช้ไฟล์ task พอ
- **ถ้าระหว่างทำแล้ว design เปลี่ยน ให้แก้ spec ก่อน แล้วค่อยแก้โค้ด**
