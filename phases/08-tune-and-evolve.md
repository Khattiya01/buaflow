# Phase 8 — ทบทวนและปรับ config (ทำซ้ำเรื่อย ๆ)

> Phase นี้ **ไม่มีวันจบ** ต่างจาก Phase 1-7 ที่ทำครั้งเดียว
> เป้าหมาย: ทำให้ config ของโปรเจกต์ **เรียนรู้** แทนที่จะแข็งค้างอยู่ที่วันแรก

## ทำเมื่อไหร่

| จังหวะ | ทำอะไร |
|---|---|
| **ปิด milestone** | ทบทวนเต็มรูปแบบ (ทุกข้อในเอกสารนี้) |
| **หลัง incident** | ทบทวนเฉพาะข้อ 8.2 และ 8.3 ทันที ห้ามรอ |
| **เปลี่ยนโมเดล** | รัน eval ทั้งชุด (ข้อ 8.4) |
| **AI พลาดเรื่องเดิม 2 ครั้ง** | ทำข้อ 8.1 ทันที ไม่ต้องรอรอบ |
| **ทุกเดือน** | ข้อ 8.5 (เก็บกวาด) |

## 8.1 เก็บบทเรียนเข้า config

รวบรวมจาก: `/review` รอบที่ผ่านมา, `docs/incidents/`, และจุดที่ต้องพิมพ์บอก AI ซ้ำ ๆ

**เลื่อนชั้นตามความรุนแรง:**

```
พลาดครั้งแรก          → แก้ในเทิร์นนั้น ไม่ต้องทำอะไรเพิ่ม
พลาดครั้งที่ 2         → AGENTS.md หมวด "สิ่งที่ AI ในโปรเจกต์นี้เคยทำผิด"
พลาดซ้ำแม้เขียนไว้แล้ว  → rule ที่ผูก paths (ถ้าผูกกับไฟล์กลุ่มหนึ่ง)
พังแล้วเจ็บจริง        → hook (บังคับ) + eval (กันถอยหลัง)
```

> เกณฑ์ที่ใช้ตัดสินว่าเลื่อนชั้นหรือยัง: **เขียนไว้แล้วแต่ยังพลาด = คำแนะนำไม่พอ ต้องบังคับ**

## 8.2 ตรวจสุขภาพของ `AGENTS.md`

- [ ] ยังไม่เกิน 200 บรรทัดใช่ไหม
- [ ] มีบรรทัดไหนที่ AI ทำถูกอยู่แล้วโดยไม่ต้องบอกไหม → **ตัดทิ้ง**
- [ ] มีกฎไหนที่ขัดกันเองไหม (AI จะเลือกเองแบบสุ่มเมื่อเจอกฎขัดกัน)
- [ ] หมวด "เคยทำผิด" ยาวเกิน 10 ข้อไหม → ข้อที่ซ้ำ ๆ ให้เลื่อนชั้นเป็น rule หรือ hook
- [ ] คำสั่งและตัวอย่าง output ยังตรงกับของจริงไหม

> อาการของ `AGENTS.md` ที่ยาวเกิน: **AI เริ่มมองข้ามกฎที่เคยทำตามได้**
> ถ้ารู้สึกว่า "บอกไปแล้วทำไมไม่ทำ" ให้สงสัยความยาวก่อนสงสัยโมเดล

## 8.3 ตรวจ rules / skills / hooks

**รันตัวตรวจก่อน แล้วค่อยใช้ตาดูส่วนที่เหลือ:**

```bash
node .claude/check-config.js
```

ข้อที่สำคัญที่สุดคือ **`paths:` ยัง match โครงจริงไหม** — โครงโฟลเดอร์ขยับเมื่อไหร่
rule จะเงียบไปเลยโดยไม่มี error บอก และไม่มีใครรู้จนกว่าจะเกิดเรื่องที่ rule นั้นควรกัน
ตัวตรวจนี้คือเหตุผลเดียวที่จะรู้ทัน

**rules — ส่วนที่ต้องใช้วิจารณญาณ (ตัวตรวจทำแทนไม่ได้)**
- [ ] rule ไหนที่ปิดแล้วผลไม่ต่าง → เขียนใหม่ให้ชัดขึ้น หรือลบ (ดูวิธีเทสในข้อ 8.4)
- [ ] เนื้อหายังตรงกับวิธีทำงานจริงไหม หรือเขียนไว้ตอนต้นโปรเจกต์แล้วทีมเปลี่ยนวิธีไปแล้ว
- [ ] ไฟล์โค้ดกลุ่มใหม่ที่เพิ่งเพิ่มเข้ามา ควรมี rule คุ้มครองไหม

**skills**
- [ ] `description` ของแต่ละตัวยังบอก **เงื่อนไขที่ควรใช้** ชัดไหม (ไม่ใช่แค่ชื่อความสามารถ)
- [ ] มี description ทับกันจน Claude เรียกผิดตัวไหม
- [ ] skill ไหนยาวเกิน ~150 บรรทัด → แยกรายละเอียดไปไฟล์ประกอบในโฟลเดอร์เดียวกัน
- [ ] skill ที่มี side effect ตั้ง `disable-model-invocation: true` ครบไหม

**ใช้ `/usage` ตรวจแทนการเดา**

`/usage` แยกให้ดูได้ว่า **skill ตัวไหน / subagent ตัวไหน / MCP server ตัวไหน กินโควต้ากี่เปอร์เซ็นต์**
(กด `d` / `w` สลับดู 24 ชั่วโมงกับ 7 วัน) และ flag พฤติกรรมที่กินเกิน 10% ให้เอง เช่น long context หรือ cache miss

อ่านตัวเลขยังไง:

| เห็นอะไร | แปลว่า | ทำอะไร |
|---|---|---|
| skill ตัวหนึ่งกินสัดส่วนสูงผิดปกติ | เขียนยาวเกิน หรือถูกเรียกในจังหวะที่ไม่ควรเรียก | ตัดให้สั้น / แก้ `description` ให้ trigger แคบลง |
| subagent กินเยอะแต่ผลลัพธ์สั้น | prompt กว้างเกินไป มันอ่านทั้งโปรเจกต์ | ระบุขอบเขตการค้นให้ชัดในตัว agent |
| flag **long context** | ไม่ค่อย `/clear` ระหว่างงานคนละเรื่อง | เตือนทีม + ดูว่า `AGENTS.md` บวมหรือยัง |
| flag **cache miss** | เปิดค้างแล้วกลับมาทำต่อข้ามชั่วโมง | ปกติของการทำงานจริง ไม่ต้องแก้ ถ้าไม่บ่อยผิดปกติ |
| MCP server กินสัดส่วนสูงทั้งที่ไม่ค่อยได้ใช้ | เปิดค้างไว้เฉย ๆ | ปิดด้วย `/mcp` |

> ข้อดีของตัวเลขชุดนี้คือ **มีให้อยู่แล้ว ไม่ต้องสร้าง dashboard** — ใช้ได้ทันทีตั้งแต่รอบแรก

**hooks**
- [ ] มี hook ไหนบล็อกงานที่ควรผ่านบ่อย ๆ ไหม → **ถือเป็นบั๊กของ hook** ให้แก้เงื่อนไขให้แคบลง
  (hook ที่ขวางบ่อยจะทำให้คนปิดทั้งชุด ซึ่งแย่กว่าไม่มี)
- [ ] ข้อความที่ hook ส่งกลับ บอก "ทางที่ถูก" ไหม ไม่ใช่แค่บอกว่าห้าม
- [ ] ถึงเวลาเปิด `Stop` hook บังคับ verify หรือยัง (ดูเงื่อนไขใน `hooks/README.md`)

## 8.4 รัน eval

รันทั้งชุดใน session ใหม่ที่สะอาด บันทึกผลลงตารางท้ายไฟล์แต่ละเคส

- เคสไหนเคยผ่านแล้วตก → **มีอะไรถอยหลัง** หาสาเหตุก่อนไปต่อ
- เคสไหนผ่านติดกันหลายรอบและไม่เคยจับอะไรได้ → พิจารณาปลดออก
- มี incident ใหม่ตั้งแต่รอบที่แล้วไหม → **ทุก incident ต้องกลายเป็น eval**

## 8.5 เก็บกวาด

- [ ] `docs/intents/` — intent ที่ค้างในสถานะ `draft` นานเกิน 1 เดือน ให้ตัดสินหรือ defer
- [ ] `docs/backlog/board.md` — task `blocked` ที่ไม่มีใครดูแล
- [ ] `docs/plans/` — plan ที่ไม่ตรงกับโค้ดที่ merge ไปแล้ว (บอกว่างานเบี่ยงจากแผนบ่อยแค่ไหน)
- [ ] `docs/specs/` — spec ที่โค้ดเปลี่ยนไปแล้วแต่ spec ยังเหมือนเดิม → **แก้ทันที** spec ที่โกหกอันตรายกว่าไม่มี

## 8.6 ตัวเลขที่ควรดู (เอาเท่าที่ดึงจาก git และ board ได้จริง)

อย่าทำ dashboard ถ้าไม่มีใครดู — เอาเท่าที่มีให้อยู่แล้วพอ

**นับเองจาก board (4 ตัว):**

| ตัวเลข | ดูอะไร | สัญญาณไม่ดี |
|---|---|---|
| task ที่ผ่าน review รอบเดียว / task ทั้งหมด | คุณภาพงานรอบแรก | ต่ำลงเรื่อย ๆ |
| ประเด็นที่รีวิวเจอซ้ำเรื่องเดิม | config ยังไม่ได้เรียนรู้ | มีเรื่องเดิมโผล่รอบที่ 3 |
| จำนวนครั้งที่ diff ไม่ตรง `plan.md` | งานหลุด scope หรือ plan ตื้นเกิน | เกิดเกือบทุก task |
| incident ที่เกิดจากสาเหตุประเภทเดิม | eval ไม่ครอบคลุม | เกิดซ้ำประเภทเดิม |

**อ่านจาก `/usage` (ไม่ต้องสร้างอะไรเลย):** สัดส่วนที่ skill / subagent / MCP แต่ละตัวกิน
และ flag พฤติกรรม — วิธีตีความอยู่ในข้อ 8.3

**สิ่งที่ยังไม่มีใครยื่นให้ และอย่าเพิ่งไปสร้าง:** dashboard ของ DORA, control band, blast radius
ทั้งสามอย่างต้องมี infra และคนดูแลจริงจัง ทำตอนที่ยังไม่มีใครอ่าน = สร้างของตายเพิ่ม

## 8.7 อัปเดตตัว kit เอง

ถ้าสิ่งที่เรียนรู้ในโปรเจกต์นี้ **ใช้ได้กับทุกโปรเจกต์** → ย้อนกลับไปแก้ที่ `project-kit/` ด้วย
แล้วเพิ่มบรรทัดใน `project-kit/VERSION.md`

นี่คือกลไกที่ทำให้ kit ดีขึ้นเรื่อย ๆ แทนที่จะแข็งค้างอยู่ที่วันที่เขียน —
**บทเรียนที่ไม่ถูกย้อนกลับไปที่ต้นทาง จะต้องเรียนใหม่ในโปรเจกต์หน้า**
