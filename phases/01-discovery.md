# Phase 1 — Discovery (เก็บ requirement)

> เป้าหมาย: ได้เอกสาร requirement ที่ละเอียดพอจะตัดสินใจ tech stack ได้ใน Phase 2
> **ห้ามแตะเรื่อง framework ใน Phase นี้** ถ้าผู้ใช้พูดถึง ให้จดไว้ใน "ข้อจำกัด" แล้วบอกว่าจะสรุปกัน Phase 2

## วิธีทำ

ถาม **ทีละกลุ่ม** กลุ่มละไม่เกิน 4 คำถาม รอคำตอบแล้วค่อยไปกลุ่มถัดไป
ทุกกลุ่ม ให้ **เดาคำตอบที่น่าจะเป็นไว้ก่อนแล้วให้ผู้ใช้แค่ยืนยัน/แก้** จะเร็วกว่าถามเปล่า
เช่น "ผมเดาว่าผู้ใช้หลักคือ X กับ Y ถูกไหมครับ / มีอีกไหม"

ถ้าโหมดเป็น `REBUILD` → อ่านโปรเจกต์เก่าแบบผ่านๆ ก่อน (route/หน้าจอ/ตาราง DB)
เพื่อ**เดา requirement ให้ผู้ใช้ยืนยัน** ไม่ต้องถามตั้งแต่ศูนย์

---

## กลุ่มคำถาม

### กลุ่ม A — ตัวโปรดักต์
1. เว็บนี้แก้ปัญหาอะไร ให้ใคร (1–2 ประโยค)
2. ผู้ใช้หลักมีกี่กลุ่ม แต่ละกลุ่มทำอะไรได้บ้าง (role)
3. อะไรคือ "สำเร็จ" ของโปรเจกต์นี้ วัดยังไง (เช่น ยอดสมัคร, ลดเวลาทำงาน X%)
4. มีคู่แข่ง/ตัวอย่างที่อยากได้คล้ายๆ ไหม

### กลุ่ม B — ขอบเขต (สำคัญที่สุด)
ให้ผู้ใช้จัด feature เป็น **MoSCoW**:
- **Must** — ไม่มีแล้วเว็บใช้ไม่ได้ (นี่คือ MVP)
- **Should** — สำคัญ แต่เลื่อนได้
- **Could** — มีก็ดี
- **Won't (ตอนนี้)** — ตัดทิ้งชัดเจน ← **ข้อนี้สำคัญมาก ต้องเขียนให้ครบ**

ถ้าโหมด `REBUILD` ให้ทำตารางเทียบเพิ่ม:

| Feature เดิม | เอาไหม | เปลี่ยนอะไร |
|---|---|---|
| ... | เอา / ไม่เอา / เอาแต่แก้ | ... |

แล้วถามเพิ่มว่า **feature ใหม่ที่จะเพิ่มจากของเดิม** มีอะไรบ้าง

### กลุ่ม C — ข้อมูลและสิทธิ์
1. Entity หลักมีอะไรบ้าง (เช่น User, Order, Product) และความสัมพันธ์คร่าวๆ
2. ปริมาณข้อมูลที่คาดว่าจะมี (หลักร้อย / หลักหมื่น / หลักล้าน แถว)
3. มีข้อมูลอ่อนไหวไหม — เลขบัตรประชาชน, ข้อมูลสุขภาพ, ข้อมูลการเงิน, ข้อมูลส่วนบุคคล
   → ถ้ามี ต้องคุย **PDPA** (ขอความยินยอม, สิทธิลบข้อมูล, retention, audit log)
4. ต้องมีระบบสิทธิ์แบบไหน — ไม่มี / ง่ายๆ 2–3 role / RBAC เต็ม / ละเอียดระดับ record

### กลุ่ม D — การเชื่อมต่อภายนอก
1. Login ผ่านอะไร — email+password, Google, LINE, Microsoft/SSO องค์กร
2. ต้องจ่ายเงินไหม — ถ้าใช่ ผ่านอะไร (Omise, Stripe, 2C2P, PromptPay QR, โอนแล้วแนบสลิป)
3. ส่งอีเมล / SMS / LINE Notify / push ไหม
4. มีระบบเดิมต้องคุยด้วยไหม (ERP, API ภายใน, ไฟล์ Excel, database เดิม)
5. อัปโหลดไฟล์/รูปไหม เก็บที่ไหน (local disk / S3 / MinIO)

### กลุ่ม E — Non-Functional Requirements
1. ผู้ใช้พร้อมกันประมาณกี่คน / ทราฟฟิกคาดหวัง
2. ต้องรองรับมือถือไหม — responsive พอ หรือต้อง PWA/app
3. รองรับ browser ไหนบ้าง (ต้องเอา IE/Safari เก่าไหม)
4. ต้องทำ SEO ไหม (มีผลใหญ่กับการเลือก SSR/SSG)
5. ต้องการ uptime แค่ไหน / มีช่วงห้ามล่มไหม
6. เป้าหมาย performance (เช่น หน้าแรกโหลด < 2 วิ, LCP < 2.5s)
7. ต้อง accessibility ระดับไหน (WCAG 2.2 AA เป็นค่าเริ่มต้นที่แนะนำ)

### กลุ่ม F — ข้อจำกัดและ Environment
1. deadline / milestone ที่มีผลจริง
2. ทีมกี่คน ใครทำอะไร (ถ้าคนเดียว + AI ก็บอกตรงๆ)
3. งบ/ข้อจำกัดเรื่อง infra (ต้อง on-prem ไหม, มี server อยู่แล้วไหม)
4. Environment: `local` / `uat` / `prd`
   - ใครเป็นคนทดสอบบน UAT (ลูกค้า? QA? ตัวเอง?)
   - มี domain แล้วหรือยัง
   - ข้อมูลบน UAT เป็นข้อมูลจริงหรือ mock

## กติกาการเขียน requirement

**ห้ามเดาแทนผู้ใช้** ทุกจุดที่ไม่ชัดและมีผลต่อผลลัพธ์ ให้เขียนเป็น
`[NEEDS CLARIFICATION: <คำถาม>]` ไว้ตรงนั้น แล้วรวมไว้ในข้อ 10 ด้วย
**ห้ามเติมค่าที่ดูสมเหตุสมผลเอาเอง** เพราะมันจะถูกอ่านผ่านและกลายเป็นข้อกำหนดจริงโดยไม่มีใครทัน

**Non-functional ต้องวัดได้** — "ต้องเร็ว" ใช้ไม่ได้
ต้องเป็น "หน้ารายการตอบภายใน 500ms ที่ข้อมูล 10,000 แถว"

> ยังไม่ต้องเขียน acceptance criteria แบบ EARS ใน Phase นี้ —
> ตรงนี้เก็บ requirement ระดับภาพรวม ส่วน AC ที่เทสได้จะไปเขียนตอน `/spec` ของแต่ละ feature

## ก่อนจบ Phase

1. เขียนไฟล์ + อัปเดต `_state.md` (Phase 1 ✅, บันทึกการตัดสินใจสำคัญ)
2. สรุปให้ผู้ใช้: **จำนวน Must feature, ความเสี่ยงสูงสุด 3 ข้อ, คำถามที่ยังค้าง**
3. ชี้จุดที่ requirement จะมีผลกับการเลือก stack (เช่น "ต้อง SEO → มีผลกับข้อ 2")
4. บอกว่า *"พิมพ์ `ทำ Phase ต่อไป` เพื่อเลือก tech stack"* แล้ว **หยุด**
