# Phase A — นำ kit ไปใช้กับโปรเจกต์ที่มีโค้ดอยู่แล้ว (โหมด EXTEND)

> ใช้ไฟล์นี้ **แทน Phase 1–6 ทั้งหมด** เมื่อ Phase 0 ตอบว่าโหมด = `EXTEND`
> จบแล้วไป **Phase 7** ตามปกติ
>
> หลักคิดต่างจากโปรเจกต์ใหม่โดยสิ้นเชิง: **ไม่ตัดสินใจอะไรใหม่ ค้นว่ามีอะไรอยู่แล้วบันทึกให้ AI รู้**
> ทุกอย่างหลังจากนี้ต้องยึดของจริงในโค้ด ไม่ใช่ค่าเริ่มต้นที่ kit สมมติไว้

---

## กฎเหล็กของ Phase นี้

1. **ห้ามเสนอเปลี่ยน stack / library / โครงสร้าง** ใน Phase นี้ — งานคือบันทึก ไม่ใช่ปรับปรุง
   ถ้าเห็นอะไรที่อยากเปลี่ยน ให้จดไว้ในข้อ A.7 แล้วปล่อยผ่าน
2. **ห้ามแก้โค้ดโปรดักชัน** ยกเว้นข้อ A.2 (ทำให้ verify ผ่าน) และต้องขอก่อนทุกครั้ง
3. **ค่าเริ่มต้นของ kit ทุกข้อเป็นแค่ "ค่าเริ่มต้น"** — ของจริงในโปรเจกต์ชนะเสมอ
   ถ้าโปรเจกต์ใช้ MUI อยู่ ธรรมนูญก็ต้องบอกว่าใช้ MUI ไม่ใช่ห้าม MUI
4. **ถามทีละกลุ่ม ไม่เกิน 4 ข้อ** และเสนอสิ่งที่เห็นในโค้ดให้ยืนยัน ไม่ใช่ถามลอย ๆ

## A.1 สำรวจ — ให้ subagent อ่าน อย่าอ่านเองใน context หลัก

ใช้ subagent `legacy-explorer` (หรือ `Explore`) ทำ inventory แล้วเอา**เฉพาะข้อสรุป**กลับมา
โปรเจกต์ที่มีอยู่แล้วมักใหญ่พอที่จะทำให้ context หลักบวมจนงานที่เหลือเสียคุณภาพ

สิ่งที่ต้องได้กลับมา เขียนลง `docs/planning/A1-inventory.md`:

| หมวด | ต้องรู้ |
|---|---|
| **Stack** | framework, ภาษา, เวอร์ชัน (อ่านจาก `package.json` / lockfile ไม่ใช่เดา), UI library, ORM, i18n lib, test runner |
| **โครงโฟลเดอร์** | ผังจริงระดับ 2-3 ชั้น + อะไรวางตรงไหน — **นี่คือสิ่งที่ `paths:` ของ rules ต้องอิง** |
| **คำสั่ง** | ทุก script ใน `package.json` และอันไหน**รันผ่านจริง** (ลองรัน อย่าเชื่อชื่อ) |
| **Convention ที่ใช้อยู่จริง** | ตั้งชื่อไฟล์, error handling, การ validate, การเรียก API, state management — ดูจากโค้ดที่เขียนซ้ำ ๆ ไม่ใช่จาก README |
| **สิ่งที่ generate อัตโนมัติ** | โฟลเดอร์ไหนห้ามแก้มือ (shadcn ui/, OpenAPI client, Prisma client, migration ที่รันแล้ว) → จะไปเป็น `protected-paths.json` |
| **เทส** | มีไหม ครอบแค่ไหน รันผ่านไหม ใช้อะไร |
| **CI/CD ที่มีอยู่** | มี pipeline อยู่แล้วไหม รันอะไร — ถ้ามี **อย่าไปแตะ** แค่บันทึก |
| **ระบบติดตามงานเดิม** | Jira / Trello / GitHub Issues / ไม่มี — มีงานค้างกี่ชิ้น |
| **เอกสารที่มี** | README, ADR, spec เดิม, wiki — อันไหนยังตรงกับโค้ด อันไหนโกหกแล้ว |

> ถ้าเจอ **เอกสารที่ไม่ตรงกับโค้ด** ให้บันทึกว่าไม่ตรง แล้ว**ถือโค้ดเป็นความจริง**
> เอกสารที่โกหกอันตรายกว่าไม่มีเอกสาร เพราะ AI จะเชื่อมัน

## A.2 ตั้ง `pnpm verify` ให้ผ่านก่อนทำอย่างอื่น

นี่คือขั้นที่**สำคัญที่สุด**และมักถูกข้าม

ทั้ง loop ของ kit (`/task` → `/review` → `/done`, hook, DoD) ยึดอยู่กับคำสั่งเดียว
ที่บอกได้ว่างานพังหรือไม่ ถ้าโค้ดเดิม typecheck ไม่ผ่านอยู่แล้ว 40 จุด AI จะแยกไม่ออกว่า
จุดไหนเป็นของเดิม จุดไหนตัวเองเพิ่งทำพัง — และจะเริ่ม "มองข้าม error" เป็นนิสัย

ทำตามลำดับ:

1. รัน `typecheck` / `lint` / `test` ที่มีอยู่ **แยกกัน** แล้วรายงานตามจริงว่าอันไหนผ่าน อันไหนไม่
2. ถ้าไม่ผ่าน เสนอผู้ใช้เลือก:

| ทางเลือก | เมื่อไหร่ |
|---|---|
| **แก้ให้ผ่าน** | ถ้า error ไม่เยอะ (< 20) และเป็นของแก้ง่าย — ทำเป็น task แรกของ backlog |
| **ตั้ง baseline** | error เยอะเกินไป → ตั้งค่า lint/tsc ให้ **ไม่ล้มกับของเก่า แต่จับของใหม่** (เช่น `--max-warnings` เท่าของเดิม, หรือ `ignore` ไฟล์เก่าเป็นรายชื่อ) แล้วเปิด intent สำหรับค่อย ๆ ลด |
| **verify แค่ส่วนที่มี** | ไม่มีเทสเลย → `verify = typecheck && lint` ไปก่อน แล้วเปิด intent "เพิ่มเทสให้ส่วนที่แตะบ่อย" |

3. เพิ่ม script `verify` ใน `package.json` ที่**รันจบใน ~30 วินาที**และ exit non-zero เมื่อพัง
4. **แปะ output ตอนผ่านไว้** — จะไปใส่ `AGENTS.md`

> ห้าม "ปิด strict" หรือ "ลบเทสที่ fail" เพื่อให้ผ่าน — นั่นคือการทำลายหลักฐาน ไม่ใช่การแก้

## A.3 ADR ย้อนหลัง — เฉพาะที่สำคัญ

AI ที่ไม่รู้ว่า "ทำไมถึงเป็นแบบนี้" จะเสนอเปลี่ยนซ้ำ ๆ ทุกครั้งที่เจอ
เขียน ADR ให้การตัดสินใจใหญ่ที่**มีอยู่แล้ว** โดยใช้ `docs/templates/adr.tpl.md`:

- สถานะ `Accepted` และระบุในบริบทว่า **"บันทึกย้อนหลัง — ตัดสินใจไปแล้วก่อนใช้ kit"**
- ถ้าไม่รู้เหตุผลจริง ให้ถามผู้ใช้ **อย่าแต่งเหตุผลเอง** ถ้าผู้ใช้ก็ไม่รู้ ให้เขียนว่า "ไม่ทราบเหตุผลเดิม"
- เขียนแค่ 3–7 ฉบับ: framework, UI library, DB/ORM, auth, โครงสร้าง, ระบบ deploy ที่มี
- **ไม่ต้องเขียน ADR ให้ทุกอย่าง** — ADR ที่ไม่มีใครอ่านคือเอกสารตาย

## A.4 ธรรมนูญแบบ "ของใหม่ vs ของเก่า"

ใช้ `docs/templates/constitution.tpl.md` แต่**มาตรา 9 ต้องต่างจากโปรเจกต์ใหม่**:

1. **บันทึกของที่ใช้อยู่จริง** ไม่ใช่ค่าเริ่มต้นของ kit — UI library, i18n มีไหม, theme ทำยังไง
2. **เพิ่มมาตรา 9.1 — กฎของใหม่กับของเก่า** (มีอยู่ในเทมเพลตแล้ว เปิดใช้):

```
- โค้ดใหม่ต้องตามมาตรฐานในธรรมนูญนี้
- โค้ดเก่าที่ไม่ตรงมาตรฐาน: ปรับ "เฉพาะไฟล์ที่กำลังแตะอยู่แล้ว" และเฉพาะส่วนที่แตะ
  ห้าม refactor ไฟล์ข้างเคียงเพราะเห็นว่าไม่ตรงมาตรฐาน
- ห้ามเปิด task "ทำให้ทั้งระบบตรงมาตรฐาน" โดยไม่มี intent ที่ผู้ใช้อนุมัติ
```

เหตุผล: ถ้าไม่มีกฎนี้ AI จะพยายาม refactor ทั้งระบบทุกครั้งที่แตะไฟล์ (เพราะเห็นว่าขัดธรรมนูญ)
หรือไม่ก็เจอกฎที่ขัดกับโค้ดเดิมจนเลือกเองแบบสุ่ม — ทั้งสองแบบแย่กว่าไม่มีธรรมนูญ

3. **ค่าเริ่มต้นของ kit ที่ยังไม่ได้ใช้** (เช่น i18n th+en, theme token) ให้ตัดสินเป็นข้อ ๆ:
   - เอา → เขียนเป็นมาตรฐานสำหรับ**ของใหม่** + เปิด intent สำหรับของเก่า
   - ไม่เอา → ตัดออกจากธรรมนูญ **และตัดออกจาก rules/AGENTS.md ด้วย** ไม่งั้นจะขัดกันเอง

## A.5 ปรับ config ให้ตรงของจริง

นี่คือส่วนที่ dry-run พิสูจน์แล้วว่า**พังเงียบได้** ทำทีละข้อแล้วรัน `check-config.js`:

| ไฟล์ | ปรับอะไร | อิงจาก |
|---|---|---|
| `.claude/rules/*.md` | `paths:` ให้ตรงโครงจริง **ลบ pattern ที่ไม่ match ทิ้ง** และแก้เนื้อหาที่อ้าง library ที่ไม่ได้ใช้ | A.1 โครงโฟลเดอร์ |
| `.claude/protected-paths.json` | รายการโฟลเดอร์ที่ generate อัตโนมัติ — **ลบ `components/ui/**` ถ้าไม่ได้ใช้ shadcn** | A.1 สิ่งที่ generate |
| `.claude/skills/*/SKILL.md` | คำสั่งที่อ้าง (`pnpm verify`, `pnpm test:api`) ต้องมีจริง / ตัดขั้นตอนที่ไม่เกี่ยว (เช่น Postman ถ้าไม่มี API) | A.1 คำสั่ง |
| `.claude/settings.json` | `permissions.allow` ตามคำสั่งจริง / `deny` ตามไฟล์ลับจริงของโปรเจกต์ | A.1 |
| `.claude/hooks/format-changed.js` | ตรวจว่า formatter/linter ที่มันมองหา ตรงกับที่โปรเจกต์ใช้ | A.1 |
| `AGENTS.md` | เขียนจาก A.1 ทั้งหมด **โดยเฉพาะ "โครงโฟลเดอร์" และ "convention ที่ใช้อยู่จริง"** | A.1 |

**เกณฑ์:** `node .claude/check-config.js` ต้องได้ `ต้องแก้: 0` และ `ควรดู:` ต้องไม่มี "pattern ที่ไม่ match" เหลืออยู่

## A.6 Source of truth ของงาน

playbook เตือนไว้ชัด: **ห้ามมี 2 sources of truth** ถ้ามีระบบติดตามงานอยู่แล้ว ต้องเลือก:

| เลือก | ทำยังไง | เหมาะเมื่อ |
|---|---|---|
| **repo เป็นหลัก** | `docs/backlog/board.md` คือความจริง ระบบเดิมเป็นแค่ที่ดู (sync ออกทางเดียว) | ทีมเล็ก ทุกคนเข้า repo ได้ |
| **ระบบเดิมเป็นหลัก** | Jira/Trello คือความจริง ไฟล์ task ใน repo เป็น**สำเนา**ที่ AI อ่าน ใส่ลิงก์กลับทุกไฟล์ | มีคนนอกทีมเทคนิคใช้ระบบเดิมอยู่ |
| **ขั้นต่ำ: ลิงก์ถึงกัน** | task ใน repo ระบุ id ของระบบเดิม / ระบบเดิมระบุ commit | ยังตัดสินไม่ได้ |

บันทึกผลลง ADR แล้ว:

- **งานค้างจากระบบเดิม → import เป็น `docs/intents/` ไม่ใช่ task** เพราะไม่รู้ว่าอันไหนยังอยากทำ
  ให้ผู้ใช้ไล่ตัดสิน ทำ/เลื่อน/ไม่ทำ ทีละอัน (ตัดทิ้งได้เยอะกว่าที่คิดเสมอ)
- สร้าง `board.md` จาก `docs/templates/backlog-board.tpl.md` เริ่มจากว่าง + intent ที่รอตัดสิน
- **task แรกของ backlog** = สิ่งที่ค้างจาก A.2 (ทำให้ verify ผ่าน) ถ้ามี

## A.7 สิ่งที่อยากเปลี่ยนแต่ยังไม่เปลี่ยน

ระหว่างสำรวจจะเจอของที่อยากแก้เต็มไปหมด — **ทั้งหมดไปที่ `docs/intents/`** ทีละอัน
ไม่ใช่ task ไม่ใช่ทำเลย เพราะแต่ละอันต้องผ่านการตัดสินเหมือนงานอื่น
